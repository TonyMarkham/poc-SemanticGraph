# GPUI Graph Layout Scheme

## Purpose

This note captures the current layout scheme for the GPUI graph visualizer research track. The target is a slick, fast, read-only semantic graph viewport with circular nodes, spline-based edges, no manual node or edge dragging, and persistent computed positions so layout does not need to be recalculated constantly.

## Graphify Findings

Graphify's main browser visualization is not a static server-side layout. Its `graph.html` path generates vis.js data and relies on browser physics/community clustering at runtime.

| Export path | Position/layout approach | Evidence |
| --- | --- | --- |
| `graph.html` | Interactive vis.js/vis-network-style physics layout with community clustering. | `to_html` is documented as an interactive vis.js HTML visualization with physics clustering, then builds `vis_nodes` and `vis_edges` JSON in [export.py](/home/tony/git/poc-SemanticGraph/submodules/graphify/graphify/export.py:627). |
| SVG export | NetworkX spring layout. | SVG export calls `nx.spring_layout(G, seed=42, k=...)` in [export.py](/home/tony/git/poc-SemanticGraph/submodules/graphify/graphify/export.py:1473). |
| Obsidian Canvas export | Deterministic community grid, with nodes arranged inside community groups. | `to_canvas` describes communities arranged in a grid and nodes in rows in [export.py](/home/tony/git/poc-SemanticGraph/submodules/graphify/graphify/export.py:1092). |
| Tree export | D3 collapsible tree view. | Graphify has a separate tree HTML export path, separate from the main graph physics path. |

Conclusion: copy Graphify's community-first idea, not its runtime browser physics model.

## Product Interaction Model

The GPUI graph viewport should be read-only for graph geometry.

| Interaction | Decision |
| --- | --- |
| Pan viewport | Allowed |
| Zoom viewport | Allowed |
| Hover node/edge | Allowed |
| Click/select node/edge | Allowed |
| Drag nodes | Not allowed |
| Drag edges | Not allowed |
| Create/edit edges in viewport | Not allowed |
| Persist user-authored node positions | Not needed |

Only viewport state is interactive: pan, zoom, hover, selection, search, filters, and active projection. Node and edge geometry is generated by layout jobs and loaded from the database.

## Rendering Scheme

The GPUI renderer should consume already-positioned graph data.

```text
SQLite graph projection
  -> layout lookup by projection/version/hash
  -> positioned nodes + edge routes
  -> GPUI graph viewport
  -> canvas draw passes + read-only hit testing
```

Rendering guidance:

| Item | Scheme |
| --- | --- |
| Nodes | Circular visual primitives. Use rounded quads for the common fast path; exact path arcs only where required. |
| Edges | Spline-based routes. Cubic Bezier paths are the default for organic graph views; straight or smooth-step paths can be used for layered views. |
| Labels | Level-of-detail dependent. Hide most labels at low zoom; show labels for selected, hovered, high-importance, or sufficiently zoomed nodes. |
| Hit testing | Use one viewport hitbox/listener plus CPU spatial hit testing in graph coordinates. Do not create one GPUI hitbox per node/edge. |
| Culling | Cull by viewport bounds before drawing nodes, edges, and labels. |
| Spatial index | Keep an in-memory grid/quadtree/R-tree per loaded projection for node/edge hover and selection. |

`gpui-flow` already demonstrates useful edge primitives: Bezier edges are painted with `PathBuilder::cubic_bezier_to` and `window.paint_path` in [edges/mod.rs](/home/tony/git/poc-SemanticGraph/submodules/gpui-flow/src/edges/mod.rs:65), and edge hit testing computes point-to-segment or point-to-cubic-Bezier distance in [edges/mod.rs](/home/tony/git/poc-SemanticGraph/submodules/gpui-flow/src/edges/mod.rs:222). The production visualizer should adapt the concepts, not necessarily the interactive node-drag behavior.

## Layout Strategy

Layout is a background/projection concern, not a paint-time concern.

```text
graph data changes
  -> projection hash changes
  -> layout marked stale or missing
  -> background layout job computes positions
  -> positions/routes persisted
  -> GPUI swaps to ready layout
```

Recommended layout modes:

| View | Layout approach |
| --- | --- |
| Whole-repo overview | Community-first layout: lay out communities first, then pack nodes inside communities. |
| Selected community | Force-directed layout using a Barnes-Hut/ForceAtlas-style engine. |
| Call/dependency chain | Dagre/Sugiyama layered layout. |
| Ownership/module tree | Deterministic tree, radial, or packed hierarchy layout. |
| Huge graph fallback | Aggregate to community/meta nodes and expand selected regions on demand. |

For large graphs, the default should be multi-level:

```text
semantic nodes
  -> communities/clusters
  -> community meta-graph layout
  -> per-community local layout
  -> optional local relaxation/no-overlap pass
```

## Rust Layout Crate Candidates

These crates are candidates for spikes, not final dependency decisions.

| Crate | Candidate use | Notes |
| --- | --- | --- |
| `fa2` | ForceAtlas2-style exploratory layout. | MIT, has Barnes-Hut and parallel paths. Good first force-layout spike. |
| `fdg-sim` | Simple force-directed prototype. | MIT, uses `petgraph`; likely easier than optimal for very large graphs. |
| `vibe-graph-layout-gpu` | GPU layout experiment. | MIT, wgpu/WebGPU, Barnes-Hut claims. Young crate; spike only. |
| `mermaid-dagre` | Directed layered layout. | MIT/Apache-2.0, Rust port of dagre, produces node coordinates and edge waypoints. |
| `dagre-dgl-rs` | Directed layered layout. | MIT, pure layout engine; outputs coordinates and edge points. |
| `layout-rs` | Graphviz-style/topological SVG-style layout. | Useful reference; less likely as core runtime layout. |
| `graphviz-rust` / `vizoxide` | Offline Graphviz integration. | Useful for export or offline precompute; less ideal as the interactive app's core layout path. |
| `petgraph` | Graph data structure base. | Not a layout engine, but a practical in-memory graph substrate for layout jobs. |

Avoid making `forceatlas2` the default production dependency without a deliberate license and toolchain decision: current crate metadata reports AGPL-3.0-only and the source uses nightly-only features.

## Position Storage Scheme

Persist layout results separately from canonical semantic graph data. Do not add `x`/`y` columns directly to canonical `nodes`, because positions depend on projection, filter, algorithm, and version.

Conceptual tables:

```sql
graph_layouts
- id
- name
- projection_key
- projection_hash
- algorithm
- algorithm_version
- params_json
- graph_version
- extraction_run_id
- status
- created_at
- updated_at

graph_node_positions
- layout_id
- node_id
- x
- y
- radius
- cluster_id
- visible
- importance
- updated_at

graph_edge_routes
- layout_id
- edge_id
- route_kind
- points_json
- visible
- updated_at
```

Suggested constraints:

```text
unique(graph_layouts.projection_hash, graph_layouts.algorithm, graph_layouts.algorithm_version, graph_layouts.params_json)
primary key(graph_node_positions.layout_id, graph_node_positions.node_id)
primary key(graph_edge_routes.layout_id, graph_edge_routes.edge_id)
```

Do not store user `pinned` or manually edited geometry fields for the current interaction model. If future requirements add manual layout editing, that should be a separate explicit design change.

## Runtime Flow

On graph open:

```text
1. Build/load graph projection.
2. Compute projection_hash from scope, filters, graph version, and layout-relevant options.
3. Find latest ready layout for projection_hash.
4. If found, render immediately.
5. If missing or stale, render loading/aggregate fallback and start background layout.
6. Persist layout rows when complete.
7. Swap or blend to the new ready layout.
```

Viewport state should remain separate from layout state:

```text
viewport_x
viewport_y
zoom
hovered_node_id
hovered_edge_id
selected_node_id
selected_edge_id
active_filter
search_query
```

Viewport state may be stored as UI preference/session state if desired, but it should not mutate the computed layout.

## Current Decision

Use cached, generated layouts:

```text
community-first projection
  -> algorithmic layout job
  -> persisted node positions and edge routes
  -> read-only GPUI renderer
  -> viewport-only drag for pan/zoom
```

This should preserve startup speed, keep the visual graph stable across sessions, avoid constant recalculation, and fit the desired high-performance GPUI rendering model.
