# VS-20: Rust Calls Layered On Route Freshness

Status: Draft implementation plan
Date: 2026-06-14

## Goal

Add Rust `calls` edges as the next provider-backed semantic relation family,
using the route freshness, route observation, stale closing, symbol mapping, and
evidence patterns established by VS-10.

The intended end state is:

- callable Rust symbols are seeded from current document-symbol nodes;
- call facts come from the pinned in-process `rust-analyzer` analysis API;
- canonical directed `calls` edges are persisted;
- callsite proof is persisted as `call` occurrences and edge evidence;
- stale call edges are soft-closed on successful reruns;
- the visualizer can inspect calls with the existing projection and edge detail
  APIs.

## Dependency On VS-10

VS-20 assumes VS-10 has already delivered:

- `extraction_route_status`;
- `route_observations`;
- store methods for route start, completion, failure, observations, and stale
  closing;
- document-symbol route observations and stale closing;
- a reliable current symbol index;
- source-location to enclosing-symbol mapping;
- grouped relation persistence with canonical edge weight;
- edge evidence and occurrence persistence patterns for provider-backed
  semantic relations.

If those pieces are not present, implement VS-10 first. Do not duplicate a
separate calls-only freshness mechanism.

## Non-Goals

- Do not add C# calls.
- Do not infer calls from raw references unless the user explicitly approves a
  fallback route.
- Do not create external dependency nodes.
- Do not model dynamic dispatch exhaustively.
- Do not add graph algorithms, call graph ranking, cycle analysis, or impact
  analysis.
- Do not add a custom call graph UI before the data exists.
- Do not shell out to a `rust-analyzer` process or CLI path.

## Current Evidence

The current schema already has the required canonical/proof fields:

- `edges.relation` can store `calls`;
- `edges.context`, `confidence`, `confidence_score`, and `weight` can describe
  call semantics and strength;
- `occurrences.role` already allows `call`;
- `edge_evidence` already stores provider method, file range, and raw JSON;
- `GraphDiagramBuilder` already has a styling branch for `calls`;
- the visualizer backend already returns edge details and evidence.

The current production extractor does not write calls. Calls appear only in demo
seed data and UI styling.

The pinned `rust-analyzer` submodule has call hierarchy handlers for prepare,
incoming calls, and outgoing calls. The outgoing route is backed by
`analysis.outgoing_calls` in the submodule handler. VS-20 should wrap the
in-process analysis API through `crates/rust-analyzer-lib`, not through the LSP
server process.

## Route Model

Add one new route:

```text
rust.calls
```

Use workspace scope for VS-20:

```text
route = "rust.calls"
scope = "workspace"
scope_key = workspace root URI
```

Workspace scope is conservative and correct for the first implementation. A
source-file change can add, remove, or retarget calls, and target resolution can
depend on broader workspace analysis. Per-file incremental calls can be added
later after the dependency and invalidation policy is explicit.

## Call Semantics

Persist calls as directed edges:

```text
caller node --calls--> callee node
```

Definitions:

- Caller node: the callable document-symbol node used as the call hierarchy
  source.
- Callee node: the canonical document-symbol node resolved from the provider's
  outgoing call target.
- Call occurrence: the callee symbol occurring at a callsite range inside the
  caller.

Canonical edge fields:

```text
relation = "calls"
context = "direct"
confidence = "EXTRACTED" when caller and callee canonical nodes are resolved
confidence_score = 1.0
weight = number of callsite ranges observed for this caller/callee edge in the current route run
```

Use `context = "direct"` because outgoing call hierarchy reports concrete
caller-to-callee call relations for the current analysis result. Do not encode
the provider method in `context`; provider details belong in evidence.

Evidence fields:

```text
provider = "rust-analyzer"
lsp_method = "callHierarchy/outgoingCalls"
file_id = caller source file
range = callsite range
raw_json includes caller symbol key, callee symbol key, provider target,
          from range, route, and target resolution mode
```

Occurrence fields:

```text
node_id = callee node
role = "call"
file_id = caller source file
range = callsite range
enclosing_node_id = caller node
```

Recursive calls are valid. A self-edge with `src_node_id = dst_node_id` should
be persisted when the provider reports it.

## Rust Analyzer Facade Work

Start with a source spike against the pinned submodule.

The spike must answer:

- which in-process `ide::Analysis` calls should be used for call hierarchy
  prepare and outgoing calls;
- which config type is required;
- how to convert provider file IDs and text ranges to UTF-16 LSP-compatible
  ranges using the existing line index approach;
- whether outgoing call targets can be mapped back to document-symbol nodes by
  file path, selection range, kind, and name;
- what happens for trait calls, method dispatch, macros, and external
  dependencies in the current pinned revision.

Expected direction from the submodule:

- prepare call hierarchy for a position;
- keep function and method items;
- request outgoing calls for the prepared item;
- collect target item plus callsite ranges.

Do not copy the LSP handler wholesale. Add a facade result shape that is stable
for this repo.

Suggested facade outputs:

```text
ResolvedOutgoingCallSet
  caller_file_path
  caller_selection_range
  caller_name
  outgoing_calls: Vec<ResolvedOutgoingCall>

ResolvedOutgoingCall
  target_file_path
  target_selection_range
  target_name
  target_kind
  callsite_ranges: Vec<TextRange>
```

If the analysis API reports multiple prepared items for one position, keep only
function/method items for VS-20 and record skipped counts in route diagnostics.

## Callable Seed Policy

Seed call hierarchy from current document-symbol nodes.

Eligible caller node kinds for VS-20:

```text
function
method
```

Optional if the provider returns them cleanly:

```text
constructor
```

Do not seed calls from modules, structs, enums, traits, fields, constants,
locals, or file nodes.

The seed position should be the callable node's selection range start. If the
provider requires a position inside the identifier, use the same convention as
document-symbol selection ranges.

## Target Mapping Policy

Map outgoing call targets to canonical document-symbol nodes.

Mapping order:

1. Exact file path plus exact selection range.
2. Exact file path plus target name and smallest symbol range containing the
   provider target range.
3. Exact file path plus target name/kind nearest to the provider target range.

If no canonical target can be found:

- skip the canonical edge;
- record a skipped-unresolved-target count in route diagnostics;
- preserve enough aggregate detail to debug the failure;
- do not create external placeholder nodes in VS-20.

If the provider target is outside the current workspace:

- skip the canonical edge;
- count it as skipped-external-target;
- do not persist an edge to a file node.

This keeps `calls` edges semantically strong. File-level fallback is acceptable
for references in VS-10, but calls should require caller and callee symbols.

## Persistence Flow

Reuse the VS-10 route lifecycle.

Recommended high-level flow:

```text
start extraction_run
refresh document symbols if the command is user-facing
start rust.calls workspace route status
extract outgoing calls for callable nodes
map caller/callee nodes
group callsite ranges by caller/callee/context
upsert calls edges
insert call occurrences
insert call edge evidence
record calls route observations
complete rust.calls route status
close stale calls edges
finish extraction_run complete
```

If extraction fails:

- mark `rust.calls` route status as failed;
- finish the run as failed;
- do not close stale calls edges.

## Edge Grouping And Weight

Group call facts by:

```text
workspace_id
caller node ID
callee node ID
relation = "calls"
context = "direct"
```

Persist one canonical edge per group. Insert one evidence row per callsite
range. Set `weight` to the number of callsite ranges in the current successful
route run.

This makes repeated calls visible without creating parallel canonical edges.

## Extractor Model Work

Add provider-neutral call model types in small module files.

Suggested types:

```text
CallExtraction
CallBatchExtraction
ExtractedCall
CallOccurrence
CallRouteSummary
```

A call extraction should include:

- provider and provider version;
- workspace root URI;
- route name;
- caller symbol identity;
- callee symbol identity;
- callsite ranges;
- raw provider metadata;
- skipped external/unresolved counts.

Keep calls separate from references. Do not represent calls as references with a
special context. Calls have different direction, source semantics, occurrence
role, and graph meaning.

## Provider Work

Extend `RustAnalyzerProvider` with a calls route:

```text
extract_rust_calls(request) -> CallBatchExtraction
```

The request should be workspace-scoped:

```text
CallBatchRequest
  workspace_root
  package_path
  file_paths
```

Implementation order:

1. Discover Rust source files with the existing workspace discovery path.
2. Refresh or load current document symbols.
3. Select callable symbol nodes.
4. Query call hierarchy prepare for each callable seed.
5. Query outgoing calls for each prepared callable item.
6. Map outgoing targets to canonical nodes.
7. Group callsite ranges by canonical edge key.
8. Emit provider-neutral call facts.

## CLI Work

Add a workspace command:

```text
semantic-graph-extract rust-workspace-calls --db <path> --workspace-root <path>
```

The command should refresh document symbols first unless VS-10 has already
introduced a shared "refresh symbols if stale" helper. The user-facing command
should not require a separate manual document-symbol run.

Optional crate-scoped command if it is straightforward:

```text
semantic-graph-extract rust-crate-calls --db <path> --workspace-root <path> --package-path <path>
```

The summary output should include call-specific counts:

```text
workspace=<id> run=<id> files=<n> callable_nodes=<n>
calls_edges=<n> call_occurrences=<n> evidence=<n>
skipped_external_targets=<n> skipped_unresolved_targets=<n>
stale_edges_closed=<n>
```

## Visualizer Work

The visualizer should already be able to show calls once data exists.

Required checks:

- `graph.projection` includes current `calls` edges when both endpoints are
  selected;
- `graph.node_details` reports incoming and outgoing `calls` relation counts;
- `graph.edge_details` shows call edge context, confidence, weight,
  properties, and callsite evidence;
- Blazor link styling uses the existing `calls` branch.

Do not add a dedicated call graph screen in VS-20. A call-specific projection
or filter belongs after canonical call data is stable.

## Acceptance Criteria

VS-20 is complete when all of the following are true:

- the Rust facade exposes provider-backed outgoing calls through the pinned
  in-process `rust-analyzer` crates;
- the calls route uses VS-10 route status and observations;
- the workspace calls command refreshes symbols and persists calls in one
  user-facing command;
- current call facts persist as canonical directed `calls` edges;
- call occurrences and edge evidence preserve callsite proof;
- repeated runs do not duplicate canonical call edges;
- edge `weight` reflects current-run callsite count;
- removing a call and rerunning the route soft-closes the corresponding
  `calls` edge;
- unresolved and external call targets are counted and skipped rather than
  represented as weak canonical nodes;
- visualizer edge and node details can inspect calls without schema errors;
- README smoke counts are updated if changed;
- the validation commands pass without warnings.

   `rust-analyzer-lib`.
3. Add facade call output types and tests.
4. Add call request/model/provider types in `semantic-graph-extract`.

10. Add visualizer backend fixtures/tests for `calls`.
11. Extend smoke tests and update README counts if needed.
12. Run validation and inspect the final diff.

## Risks And Decisions To Preserve

- Outgoing call hierarchy may omit dynamic dispatch, macro-expanded calls, or
  calls hidden behind unresolved analysis. Do not overstate completeness.
- Trait and method dispatch may resolve differently depending on available
  workspace metadata. Preserve raw provider evidence for debugging.
- External dependency calls are intentionally skipped until external symbol
  identity is designed.
- Calls should be stricter than references: require symbol-to-symbol mapping
  and skip unresolved targets.
- A dense call graph can clutter the existing projection. Add filters only
  after the canonical data path is stable.
