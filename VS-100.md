# VS-100: SemanticGraph MCP, Agents, And Skills

## Goal

Build a SemanticGraph-native MCP, agent, and skill surface inspired by Graphify,
but tailored to this repository's durable SQLite graph, language-server-backed
Rust and C# extraction.

The intended result is:

- a read-only MCP server that lets agents query the existing SQLite semantic
  graph with evidence;
- an explicitly gated extraction MCP surface for graph refresh commands;
- generated project-local skill and agent definitions that teach agents to use
  the graph before broad source inspection;
- drift checks so generated skill and agent artifacts stay consistent with the
  actual command and MCP tool surface.

Treat Graphify as a reference for ergonomics, not as a dependency. Copy the
useful patterns: small graph tools, query-first skill guidance, generated
platform-specific artifacts, and progressive references. Do not copy its weaker
parts: ambiguous install flows, inconsistent Codex agent handoffs, stale
security claims, or unauthenticated non-loopback HTTP by default.

This document is the initiative outline. Concrete Phase 0 decisions that
downstream phases must follow are recorded in [VS-1000.md](VS-1000.md).

## Current Evidence

Graphify provides useful local reference points:

- `submodules/graphify/graphify/serve.py` exposes an MCP server with tools such
  as `query_graph`, `get_node`, `get_neighbors`, `graph_stats`, and
  `shortest_path`.
- `submodules/graphify/graphify/mcp_ingest.py` treats MCP config files as a
  corpus input while avoiding persistence of secret values.
- `submodules/graphify/tools/skillgen/` generates platform-specific skills from
  shared fragments and checks the committed output for drift.
- `submodules/graphify/graphify/skill-codex.md` shows why Codex-specific agent
  instructions need their own handoff contract instead of inheriting
  Claude-style chunk-file assumptions.
- `submodules/graphify/graphify/always_on/agents-md.md` is the right ergonomic
  idea for always-on graph orientation: query first, then inspect source only
  when needed.

This repository already has the surfaces a SemanticGraph agent system should
wrap:

- `crates/semantic-graph-store` owns the SQLite schema and migrations.
- `crates/semantic-graph-db-manager` owns write-side graph refresh, stale
  closing, route status, and provenance.
- `crates/semantic-graph-extract` exposes Rust and C# extraction command
  families.
- `crates/rust-analyzer-lib` and `crates/csharp-ls-lib` provide language
  intelligence facade layers.
- `crates/semantic-graph-visualizer-server` already has read-only graph query
  logic for `graph.projection`, `graph.node_details`, `graph.edge_details`, and
  `graph.search_nodes`.
- `apps/SemanticGraph.Visualizer` and
  `crates/semantic-graph-visualizer-server` are current local testbed surfaces.
  They were added to provide a C# project and a convenient graph projection
  smoke path, not as durable product targets for this repo.

## Non-Goals

- Do not treat the current Blazor visualizer or JSON-RPC backend as durable
  product targets. They may inform query shape and smoke coverage while they
  exist, but the MCP and query surfaces must stand on their own.
- Do not make Graphify a runtime dependency.
- Do not expose arbitrary SQL, arbitrary shell commands, or raw file reads as
  MCP tools.
- Do not make mutating extraction tools available in the default MCP server.
- Do not install global skills or modify a user's home directory in the first
  implementation slice.
- Do not introduce LLM-authored semantic graph facts as canonical data. The
  durable graph remains language-server-backed evidence plus explicit
  provenance.

## Design Principles

Use SQLite as the source of truth.

Agents should query canonical nodes, edges, occurrences, edge evidence, and
route freshness from the database. Source-file inspection is a follow-up when
the graph does not contain enough evidence, not the default starting point.

Split read and write capabilities.

The default MCP server is read-only. Extraction and stale-marking tools are
either a separate binary or require an explicit `--enable-extract-tools` flag.
This avoids giving every MCP client write authority just because it can inspect
the graph.

Prefer stdio first.

The first MCP transport is stdio for local agent hosts. HTTP can be added only
with loopback defaults, an API key for any non-loopback bind, and an explicit
danger flag for unauthenticated shared service experiments.

Make security behavior true in code and docs.

Every public tool and resource needs bounded output, validated parameters,
clear path rules, and consistent text sanitization. Security docs must describe
the implementation that exists, not the one that used to exist.

Generate agent assets from one manifest.

Human-edited fragments should produce platform-specific `SKILL.md` files,
custom-agent templates, and always-on snippets. A check command must fail when
generated artifacts drift from the source fragments.

Keep host handoffs host-specific.

Codex, Claude, OpenCode, and generic MCP clients do not share identical agent
APIs. Shared conceptual steps are fine, but the generated instructions must not
ask Codex to use Claude-style chunk files or tool-result fields that do not
exist.

## Proposed Repository Shape

Add new project-owned surfaces:

```text
crates/semantic-graph-query
  Shared read-only query service and DTOs used by MCP and any local testbed
  consumers.

crates/semantic-graph-mcp-server
  Agent-facing MCP server binary/library.

crates/semantic-graph-cli
  Top-level user-facing CLI that exposes `semantic-graph install codex` and
  delegates generation, MCP registration, and local project setup.

crates/semantic-graph-agent-assets
  Generator/checker for skills, custom-agent templates, and always-on snippets.

agent-assets/
  manifest.toml
  fragments/
  expected/
```

The exact crate names can change during implementation, but keep this ownership
split:

- query code is independent of transport;
- MCP code owns MCP transport, tool schemas, and resource schemas;
- generated agent/skill artifacts are build-time or developer-time assets, not
  runtime query code.

The current `semantic-graph-visualizer-server::query` module is useful prior
art, but it should not become the durable query boundary. Extract
`semantic-graph-query` in the first shared-query slice so MCP models are not
shaped by visualizer DTO names.

## MCP Server Slice 1: Read-Only Graph Query

Add a read-only MCP server with this command shape:

```sh
semantic-graph-mcp-server \
  --database-path .local/rust-workspace-extract.db \
  --transport stdio
```

Optional HTTP is a later or same-slice transport only if it has safe defaults:

```sh
semantic-graph-mcp-server \
  --database-path .local/rust-workspace-extract.db \
  --transport http \
  --bind 127.0.0.1:5181 \
  --api-key-env SEMANTIC_GRAPH_MCP_API_KEY
```

Rules:

- default transport is stdio;
- default HTTP bind is loopback only;
- binding to `0.0.0.0` or `[::]` requires an API key;
- unauthenticated non-loopback HTTP requires an explicit
  `--allow-unauthenticated-non-loopback` flag and prints a warning;
- CORS is disabled unless explicitly configured for a local browser client;
- the server opens SQLite read-only for query tools.

Initial tools:

| Tool | Purpose |
| --- | --- |
| `graph_search_nodes` | Search active nodes by name, qualified name, display label, or source path. |
| `graph_node_details` | Return one node with relation summaries and occurrences. |
| `graph_edge_details` | Return one edge with endpoints and evidence. |
| `graph_projection` | Return a bounded graph projection derived from the current query shape. |
| `graph_neighbors` | Return bounded incoming/outgoing neighbors for a node. |
| `graph_shortest_path` | Return a bounded path between two node ids using active edges. |
| `graph_file_summary` | Return file node, contained symbols, and active route freshness for one file path. |
| `graph_route_status` | Return latest route status by workspace, file, route name, and scope. |
| `graph_stats` | Return row counts and latest extraction run metadata. |

Initial resources:

| Resource | Purpose |
| --- | --- |
| `semantic-graph://schema` | Human-readable graph schema summary. |
| `semantic-graph://workspace` | Current database path, workspaces, languages, and latest runs. |
| `semantic-graph://routes` | Route names and freshness semantics. |
| `semantic-graph://local-testbeds` | Optional current local smoke/testbed surfaces for this database, if present. |

Tool output rules:

- never return more than the requested limit or the server-side max limit;
- include node ids and edge ids so agents can follow up precisely;
- include occurrence/evidence ids where possible;
- include `valid_to_run_id` or stale state when relevant;
- sanitize graph-originated strings before embedding them in plain text;
- prefer structured JSON content over prose blobs so agents do not have to
  parse human-oriented text.

## MCP Server Slice 2: Optional Extraction Tools

Add mutating tools only behind an explicit gate:

```sh
semantic-graph-mcp-server \
  --database-path .local/rust-workspace-extract.db \
  --transport stdio \
  --enable-extract-tools \
  --workspace-root .
```

Candidate tools:

| Tool | Maps To |
| --- | --- |
| `extract_rust_file` | `semantic-graph-extract rust-file` |
| `extract_rust_file_deleted` | `semantic-graph-extract rust-file-deleted` |
| `extract_rust_crate` | `semantic-graph-extract rust-crate` |
| `extract_rust_workspace` | `semantic-graph-extract rust-workspace` |
| `extract_csharp_file` | `semantic-graph-extract csharp-file` |
| `extract_csharp_file_deleted` | `semantic-graph-extract csharp-file-deleted` |
| `extract_csharp_project` | `semantic-graph-extract csharp-project` |
| `extract_csharp_solution` | `semantic-graph-extract csharp-solution` |

Implementation constraints:

- prefer library calls over spawning a shell;
- if invoking a binary is necessary, construct argv directly and do not pass
  user input through a shell string;
- require all file and workspace paths to resolve under the configured
  `--workspace-root`;
- require relation-only routes to follow the existing rule that symbols must
  already exist unless the same invocation includes symbols;
- return the same summary counts the CLI prints today;
- record route failures exactly as the current extractor does;
- do not expose delete, reset, or hard-prune operations.

This slice should be implemented after the read-only server is useful. It is
acceptable for the first merged MCP server to be read-only.

## Agent Definitions

Create project-local Codex custom-agent templates generated from shared
fragments.
These are not durable graph data. They are operational prompts that tell agent
hosts how to use the MCP/query/extraction surfaces.

Initial custom-agent templates:

| Agent | Responsibility |
| --- | --- |
| `semantic-graph-explorer` | Query MCP for orientation, inspect node/edge evidence, and report graph-backed findings. |
| `semantic-graph-route-verifier` | Compare extractor route expectations against DB route status and smoke-test output. |
| `semantic-graph-rust-refresh` | Refresh Rust file/crate/workspace graph facts using the approved extractor commands. |
| `semantic-graph-csharp-refresh` | Refresh C# file/project/solution graph facts using the approved extractor commands. |
| `semantic-graph-plan-auditor` | Review implementation plans against graph evidence, ADRs, and repository constraints. |

Agent handoff contract:

- each agent receives the database path, workspace root, allowed mutation flag,
  and the exact MCP tools or CLI commands it may use;
- read-only agents must not run extraction commands;
- refresh agents must report the command, route selectors, summary counts, and
  validation performed;
- agents return structured Markdown with `Confirmed`, `Inferred`, `Unknown`,
  and `Validation` sections when precision matters;
- no agent contract relies on temporary chunk files unless the same generated
  host variant explicitly instructs that agent to write those files;
- Codex variants must refer to Codex's current multi-agent concepts only in the
  Codex-specific fragment, not in shared fragments.

Do not require subagents for normal graph querying. The graph query path should
be deterministic and fast enough for the primary agent to use directly.
Subagents are useful for independent audits, route verification, and broader
planning passes.

Do not generate or install a smoke-test custom agent for downstream projects.
Smoke verification is valuable in this development repository, but it belongs
in deterministic tests, `doctor codex`, or a future developer-only smoke
command rather than as a project-installed agent artifact.

## Skill Definitions

Create a `semantic-graph` skill for Codex first, with room for later platform
variants.

Planned project-local Codex output:

```text
.agents/skills/semantic-graph/SKILL.md
.agents/skills/semantic-graph/references/mcp-tools.md
.agents/skills/semantic-graph/references/rust-extraction.md
.agents/skills/semantic-graph/references/csharp-extraction.md
.agents/skills/semantic-graph/references/local-testbeds.md
.agents/skills/semantic-graph/references/agent-handoffs.md
.agents/skills/semantic-graph/references/troubleshooting.md
```

Skill trigger guidance:

- use this skill when the user asks about code relationships, call graphs,
  references, source provenance, stale extraction, query surfaces, or semantic
  graph refresh;
- use this skill before broad source exploration when a SemanticGraph database
  exists;
- do not use this skill for tiny direct code edits where the relevant file and
  line are already known.

Core skill workflow:

1. Resolve the database path using the shared SemanticGraph config precedence.
2. Check graph availability with `graph_stats` or the equivalent CLI stats
   command.
3. Search for relevant nodes before reading arbitrary source files.
4. Use node details, edge details, occurrences, and edge evidence to ground the
   answer.
5. Check route freshness when the user asks about current behavior or recently
   changed files.
6. Refresh the graph only when the user asked for implementation, refresh, or
   validation work that requires current graph facts.
7. Cite source files or DB evidence in the final answer; label uncertain
   inferences clearly.

The skill must avoid absolute "always query first" language for requests where
the graph is not relevant. It should instead say to query the graph first for
relationship, dependency, reference, call, query-surface, or provenance work.

## Always-On Project Guidance

Add an optional generated AGENTS block only after the skill and MCP server are
stable. The root `AGENTS.md` already contains repository-critical instructions,
so any generated block must be clearly delimited and preserve existing content.

Proposed marker format:

```md
<!-- BEGIN SEMANTIC_GRAPH_AGENT_GUIDANCE -->
...
<!-- END SEMANTIC_GRAPH_AGENT_GUIDANCE -->
```

The block should say:

- when a SemanticGraph database is available, use MCP or other read-only graph
  query methods for graph-oriented questions before broad source reads;
- extraction commands mutate SQLite and should be run only when the task calls
  for refresh or validation;
- stale graph facts must be reported as stale, not silently treated as current;
- graph evidence does not replace source inspection when editing code.

Do not overwrite the whole `AGENTS.md`.

## Dedicated Codex Install CLI

Add a user-facing CLI binary named `semantic-graph` with a dedicated Codex
installer:

```sh
semantic-graph install codex
```

The default command installs repo-local Codex resources into the current
repository. It must not write to `$HOME`, `/etc`, or any user-global Codex
configuration.

Supported command shape:

```sh
semantic-graph install codex \
  --project . \
  --database-path .local/rust-workspace-extract.db \
  --mcp read-only

semantic-graph install codex --mcp disabled
semantic-graph install codex --mcp read-only
semantic-graph install codex --mcp extract --enable-extract-tools
semantic-graph install codex --dry-run
semantic-graph install codex --force
semantic-graph uninstall codex
semantic-graph doctor codex
```

Defaults:

- `--project` defaults to the current working directory;
- `--mcp` defaults to `read-only`;
- `--database-path` defaults to normal SemanticGraph database resolution when
  possible, otherwise writes the MCP server config with
  `.local/rust-workspace-extract.db`;
- install is idempotent;
- existing user-authored files are preserved unless they are recorded in
  `.codex/semantic-graph/install-manifest.json` or `--force` is passed.

The installer writes these Codex-compatible local resources:

| Path | Purpose |
| --- | --- |
| `.agents/skills/semantic-graph/SKILL.md` | Repo-scoped Codex skill. |
| `.agents/skills/semantic-graph/references/*.md` | Progressive reference files for the skill. |
| `.codex/agents/*.toml` | Project-scoped custom agents for graph exploration, refresh, route verification, and plan audits. |
| `.codex/config.toml` | Project-scoped Codex config updated with the SemanticGraph MCP server. |
| `.codex/semantic-graph/install-manifest.json` | Managed-file manifest for idempotent reinstall and safe uninstall. |

The installer must update `.codex/config.toml` structurally as TOML instead of
with string concatenation. It should preserve unrelated settings such as
`developer_instructions`, existing MCP servers, model settings, and user-authored
agent configuration.

Default MCP config snippet:

```toml
[mcp_servers.semantic_graph]
command = "target/release/semantic-graph-mcp-server"
args = [
  "--database-path",
  ".local/rust-workspace-extract.db",
  "--transport",
  "stdio",
]
enabled = true
required = false
startup_timeout_sec = 10
tool_timeout_sec = 60
```

When `--mcp extract --enable-extract-tools` is selected, append
`"--enable-extract-tools"` and `"--workspace-root", "."` to the MCP server args.
The installer must not enable mutating MCP tools unless both the mode and the
explicit extract flag are present.

Custom agent files under `.codex/agents/` must follow Codex's project-scoped
custom-agent shape:

```toml
name = "semantic-graph-explorer"
description = "Use SemanticGraph MCP tools to answer code relationship questions with graph evidence."
developer_instructions = """
Query the SemanticGraph MCP server before broad source inspection. Use node,
edge, occurrence, evidence, route status, and stats tools to ground findings.
Do not run extraction commands.
"""
```

Installer implementation requirements:

- create parent directories with explicit, narrow writes;
- write generated files through temp files plus atomic rename where practical;
- format TOML deterministically;
- print every path created, updated, skipped, or refused;
- keep a manifest of managed files and checksums;
- refuse to overwrite untracked user-authored content unless `--force` is
  passed;
- add `.codex/semantic-graph/README.md` explaining the local resources and how
  to remove them;
- never modify `AGENTS.md` unless a later explicit flag such as
  `--with-agents-md-block` is implemented.

`semantic-graph doctor codex` should verify:

- `.agents/skills/semantic-graph/SKILL.md` exists and has `name` and
  `description`;
- expected skill references exist;
- each `.codex/agents/*.toml` file parses and has required fields;
- `.codex/config.toml` contains an enabled or intentionally disabled
  `[mcp_servers.semantic_graph]` table;
- the configured MCP command exists or can be built from the workspace;
- the MCP server can start in stdio mode and answer `graph_stats` when the
  database exists.

Installer tests should cover:

- fresh install into an empty temporary repo;
- install into a repo with an existing `.codex/config.toml`;
- preservation of unrelated config keys and unrelated MCP server tables;
- refusal to overwrite user-authored skill or agent files;
- `--force` replacement of managed files only;
- safe uninstall using the manifest;
- `--mcp disabled`, `--mcp read-only`, and gated `--mcp extract` output;
- `doctor codex` success and actionable failure messages.

## Optional Agent Artifact Extraction

After the skill/MCP surface is stable, consider a separate extraction route for
agent-facing configuration files:

- `AGENTS.md`;
- `.agents/skills/*/SKILL.md`;
- `.agents/skills/*/references/*.md`;
- `.codex/agents/*.toml`;
- `.mcp.json`;
- `.cursor/rules/*`;
- other project-local agent configuration files.

This route would let SemanticGraph model how agent guidance, MCP tools, and
project instructions relate to code extraction workflows. A local UI testbed
could display those relationships while it exists, but the extraction route
should not depend on that UI. It should follow Graphify's MCP config ingestion
discipline:

- store config keys, server names, command names, package names, and env var
  names;
- do not store env var values, token values, or positional arguments likely to
  contain secrets;
- cap file size;
- only ingest recognized config filenames unless the user explicitly passes a
  file.

This is not required for the first MCP server or skill slice.

## Implementation Plan

### Phase 1: Shared Query Surface

- Extract read-only query code from the current visualizer-server prior art
  into a durable shared query crate.
- Add query methods for stats, neighbors, shortest path, file summary, and
  route status.
- Keep DTOs transport-neutral where possible. MCP-specific and optional local
  testbed DTOs can wrap shared query models.
- Add tests using seeded SQLite fixtures for each new query method.

### Phase 2: Read-Only MCP Server

- Add `crates/semantic-graph-mcp-server` to the workspace.
- Choose the Rust MCP implementation after a small spike; if no dependency is
  mature enough, implement the narrow stdio JSON-RPC/MCP subset needed for the
  initial tools.
- Implement stdio transport first.
- Add HTTP transport only with loopback and API-key rules.
- Add tool schemas and resources listed in this plan.
- Add integration tests that call the MCP server over stdio against a fixture
  database.
- Add README examples for registering the stdio server with an MCP-compatible
  host.

### Phase 3: Skill And Agent Asset Generator

- Add `crates/semantic-graph-agent-assets` or an equivalent repo-owned
  generator.
- Add `crates/semantic-graph-cli` with a `semantic-graph` binary.
- Add manifest, fragments, expected artifacts, and project-local install.
- Generate the Codex skill and reference files first.
- Generate project-scoped Codex custom-agent TOML files first.
- Implement `semantic-graph install codex`, `semantic-graph uninstall codex`,
  and `semantic-graph doctor codex`.
- Add tests that prevent stale command names and platform handoff drift.
- Add tests that install into a temporary repo and verify `.agents/skills`,
  `.codex/agents`, `.codex/config.toml`, and the install manifest.

### Phase 4: Optional Extraction MCP Tools

- Add `--enable-extract-tools`.
- Implement Rust extraction tools first because the Rust route surface is the
  most mature.
- Add C# extraction tools after verifying the current C# command behavior and
  smoke tests.
- Enforce workspace-root path validation.
- Return structured extraction summaries and route status.
- Add tests for disabled-by-default behavior and path rejection.

### Phase 5: Documentation And Local Testbed Notes

- Update `README.md` with MCP server startup, skill install, and validation
  examples.
- If the local visualizer testbed still exists, document it as an optional
  smoke surface and C# extraction test project, not as a durable target.
- Document the difference between read-only graph query, extraction refresh,
  and optional local testbed inspection.

## Suggested Implementation Phase Breakdown

Use this sequence when turning the plan into patches. Each phase should be
mergeable on its own and should leave the repo in a validated state.

| Phase | Primary Slice | Depends On | Merge Gate |
| --- | --- | --- | --- |
| 0 | Preflight decisions | Existing repo only | Short note in `VS-100.md` or follow-up issue records MCP SDK choice, query crate decision, and Codex local resource paths. |
| 1 | Shared read-only query API | Phase 0 | Query methods for stats, neighbors, shortest path, file summary, and route status have fixture tests. |
| 2 | Read-only MCP stdio MVP | Phase 1 | Stdio MCP server starts against a fixture database and answers core read tools. |
| 3 | Codex asset generator | Phase 2 can run in parallel after tool schemas stabilize | Generated Codex skill, references, custom-agent TOML files, and MCP config snippet match expected snapshots. |
| 4 | `semantic-graph install codex` | Phase 3 | Fresh temp-repo install writes `.agents/skills`, `.codex/agents`, `.codex/config.toml`, and manifest without global writes. |
| 5 | Installer hardening | Phase 4 | Reinstall, `--dry-run`, `--force`, uninstall, and preservation of unrelated Codex config are tested. |
| 6 | `semantic-graph doctor codex` | Phase 4 | Doctor reports success for a valid install and actionable failures for missing skill, agent, MCP command, and database. |
| 7 | Optional extraction MCP tools | Phase 2, Rust/C# route confidence | Mutating tools remain disabled by default and pass path-scope and route-selector tests. |
| 8 | Documentation and end-to-end smoke | Phases 2, 4, 6 | README examples work for install, MCP startup, graph query, doctor, and uninstall. Optional local testbed smoke is documented only if the testbed remains present. |

Phase 0 should be deliberately small. Confirm the Codex repo-local paths used
by this plan, record that `semantic-graph-query` is the durable Phase 1 query
boundary, and choose an MCP SDK or narrow local MCP implementation. Do not
implement installer behavior in this phase.

Phase 1 should avoid MCP concerns. The goal is a transport-neutral query layer
that can be consumed by the MCP server and any optional local testbed while it
exists. Keep this slice read-only and SQLite-backed.

Phase 2 should expose only read tools over stdio. Do not add HTTP transport or
mutating extraction tools in the MVP unless the read-only stdio server is
already validated. The first useful smoke path is `graph_stats`,
`graph_search_nodes`, `graph_node_details`, and `graph_edge_details`.

Phase 3 should generate artifacts but not install them. The key output is a
stable expected-artifact tree for Codex-compatible local resources:
`.agents/skills`, `.codex/agents`, and a SemanticGraph MCP config snippet.

Phase 4 should make `semantic-graph install codex` the first polished user
workflow. Prefer a small CLI surface over broad options: `install codex`,
`--project`, `--database-path`, `--mcp`, `--dry-run`, and `--force` are enough
for the first installer slice.

Phase 5 should focus on safety. The installer must be idempotent, preserve
unrelated `.codex/config.toml` content, refuse to overwrite user-authored files
by default, and uninstall only files recorded in the manifest.

Phase 6 should make failure modes legible. `semantic-graph doctor codex` should
not mutate files; it should inspect the install, check parseability, and explain
the exact command or file edit needed to repair each problem.

Phase 7 is intentionally late. Mutating MCP tools expand the blast radius, so
they should wait until the read-only MCP server, installer, and doctor flows are
boring and well tested.

Phase 8 should close the loop with docs and smoke tests. The README should show
the same command sequence a user would run from a clean repo:

```sh
cargo build --release \
  -p semantic-graph-mcp-server \
  -p semantic-graph-cli

./target/release/semantic-graph install codex --project .
./target/release/semantic-graph doctor codex --project .
```

## Security Requirements

- The default server is read-only and stdio-only.
- HTTP defaults to `127.0.0.1`.
- Non-loopback HTTP requires an API key unless an explicit danger flag is
  passed.
- No arbitrary SQL tool.
- No arbitrary shell command tool.
- No raw file read tool.
- All SQL uses bound parameters.
- All outputs have server-side limits.
- All graph-originated strings embedded in text responses pass through one
  shared sanitization helper.
- Structured JSON fields may preserve exact values, but text summaries must be
  safe to display in agent transcripts.
- Mutating tools validate paths under `--workspace-root`.
- Mutating tools are disabled unless explicitly enabled.
- Security docs and CLI help must be updated in the same change as any
  transport or authorization behavior.

## Acceptance Criteria

- Agents can query graph facts through MCP without reading source files first.
- The MCP server exposes evidence-rich node and edge details, not just labels.
- Read-only MCP tools cannot mutate the SQLite graph.
- Extraction MCP tools are disabled by default and path-scoped when enabled.
- Codex skill instructions match Codex behavior and do not mention
  incompatible agent handoffs.
- Generated skills, references, and custom-agent TOML files have a drift check.
- `semantic-graph install codex` writes repo-local `.agents/skills`,
  `.codex/agents`, and `.codex/config.toml` resources compatible with Codex.
- `semantic-graph uninstall codex` removes only manifest-managed resources.
- `semantic-graph doctor codex` reports actionable setup problems.
- Project-local install is deterministic and does not touch user-global
  directories.
- README examples match the actual command surface.

## Open Questions

- Should any local UI/testbed host share a process with the MCP server? The
  safer first implementation is a separate MCP binary over a shared query
  crate.
- Which Rust MCP SDK, if any, should be adopted? Decide during Phase 2 with a
  small spike instead of baking an unverified dependency into this plan.
- Should extraction MCP tools call extractor library functions directly or
  invoke the release binary with typed argv? Prefer library calls, but preserve
  current CLI behavior if that is the narrower first step.
- Should agent asset generation live in a Rust crate or a small standalone tool?
  Prefer Rust if it keeps workspace validation simple.
- Should the optional agent artifact extraction route become part of the normal
  semantic graph, or remain a separate metadata graph? Defer until MCP and skill
  workflows are stable.
