# VS-1300: Phase 3 Implementation Plan For Codex Asset Generation

## Purpose

Define the implementation plan for Phase 3 of [VS-100.md](VS-100.md):
creating the repo-owned generator for SemanticGraph Codex skills, references,
custom-agent templates, and MCP configuration snippets.

This plan follows the accepted decisions in [VS-1000.md](VS-1000.md). In
particular:

- Generated Codex assets are project-local and use `.agents/skills`,
  `.codex/agents`, and Codex project config paths.
- The generated MCP config table name is `[mcp_servers.semantic_graph]`.
- Downstream custom agents are limited to graph exploration, route
  verification, Rust refresh, C# refresh, and plan auditing.
- Do not generate or install a smoke-test custom agent for downstream projects.
- Preserve existing SemanticGraph database config compatibility; do not rename
  or migrate `.refactor-radar/config.toml`.
- The current Blazor/JSON-RPC visualizer remains only a local testbed and must
  not define the generated agent asset boundary.

## Phase Boundary

`VS-100.md` contains both a broad Phase 3 outline and a more granular
mergeable phase breakdown. This plan uses the granular Phase 3 boundary:
generate artifacts and drift checks, but do not install them into a project.

Follow-on plans should cover:

- `semantic-graph install codex`;
- `semantic-graph uninstall codex`;
- installer safety, `--dry-run`, `--force`, and manifest behavior;
- `semantic-graph doctor codex`;
- optional extraction MCP tools.

The Phase 3 output is the stable source and expected-artifact tree those later
installer phases will consume.

## Goal

Add a new workspace crate:

```text
crates/semantic-graph-agent-assets
```

The crate owns deterministic generation and drift checking for Codex-compatible
SemanticGraph assets:

- the `semantic-graph` Codex skill;
- progressive skill reference files;
- project-scoped Codex custom-agent TOML templates;
- a SemanticGraph MCP config snippet using `[mcp_servers.semantic_graph]`;
- a local generated README for the future managed Codex install directory.

The generator command surface is:

```sh
semantic-graph-agent-assets generate
semantic-graph-agent-assets check
```

`generate` updates checked-in expected artifacts. `check` regenerates into a
temporary location and fails when checked-in expected artifacts drift.

## Non-Goals

- Do not implement `semantic-graph-cli`.
- Do not implement `semantic-graph install codex`.
- Do not implement `semantic-graph uninstall codex`.
- Do not implement `semantic-graph doctor codex`.
- Do not write generated assets into `.agents/`, `.codex/`, `$HOME`, `/etc`,
  or any user-global location.
- Do not modify `AGENTS.md`.
- Do not add an always-on generated AGENTS block.
- Do not add mutating extraction MCP tools or `--enable-extract-tools`.
- Do not add HTTP transport.
- Do not add a smoke-test custom agent.
- Do not make Graphify a runtime dependency.
- Do not duplicate durable graph query behavior in the asset generator.
- Do not expose arbitrary SQL, arbitrary shell commands, or raw file reads.
- Do not change `.refactor-radar/config.toml` compatibility behavior.
- Do not update the visualizer server or Blazor client as part of Phase 3.

## Crate Ownership

`semantic-graph-agent-assets` should own:

- parsing the asset manifest;
- loading source fragments;
- deterministic rendering of Codex skill/reference files;
- deterministic rendering of custom-agent TOML files;
- deterministic rendering of a SemanticGraph MCP config snippet;
- deterministic rendering of `.codex/semantic-graph/README.md`;
- expected-artifact drift checking;
- tests that prevent stale command names and host handoff drift.

`semantic-graph-agent-assets` should not own:

- MCP protocol handling;
- graph database queries;
- graph extraction or refresh orchestration;
- project installation or uninstall behavior;
- `.codex/config.toml` structural merge behavior;
- install manifests, checksums, or managed-file ownership decisions;
- user-global Codex configuration.

Later installer work can call this crate as a library or invoke its generated
artifact definitions, but installer policy must remain outside Phase 3.

## Source Asset Tree

Add source inputs under `agent-assets/`:

```text
agent-assets/manifest.toml
agent-assets/fragments/common/*.md
agent-assets/fragments/codex/*.md
agent-assets/fragments/agents/*.md
```

The manifest should define:

- the skill name, description, and output references;
- the supported host variant, initially `codex`;
- the generated custom-agent names and descriptions;
- the MCP server table name, `semantic_graph`;
- the default MCP command, `.refactor-radar/bin/semantic-graph-mcp-server`;
- the default MCP args for read-only stdio startup, initially empty so the
  server uses existing SemanticGraph config discovery;
- the generated output paths under the expected-artifact tree.

Fragments should be small and host-aware:

- common fragments may describe SemanticGraph concepts, query-first workflow,
  route freshness, stale state, evidence handling, and read-only vs refresh
  boundaries;
- Codex fragments own Codex-specific skill and custom-agent wording;
- agent fragments own the responsibilities and handoff contracts for each
  generated custom agent.

Shared fragments must not mention Claude-only chunk files, host-specific tool
result fields from another system, or unsupported Codex behavior.

## Skill Contract

Generate a Codex skill at:

```text
.agents/skills/semantic-graph/SKILL.md
```

The generated skill should trigger for:

- code relationship questions;
- call graph, reference, and dependency questions;
- source provenance and evidence questions;
- stale extraction and route freshness questions;
- SemanticGraph MCP query work;
- semantic graph refresh planning or validation work.

The generated skill should not claim that every request must query the graph
first. It should say to query the graph first when the user's task is about
relationships, references, calls, provenance, route freshness, query surfaces,
or semantic graph refresh.

Core generated workflow:

1. Resolve the database path using existing SemanticGraph config behavior or
   the configured MCP server.
2. Check graph availability with `graph_stats`.
3. Search relevant nodes before broad source inspection.
4. Use node details, edge details, occurrences, and edge evidence to ground
   findings.
5. Check route freshness when current behavior or recently changed files
   matter.
6. Refresh the graph only when the user asked for implementation, refresh, or
   validation work that requires current graph facts.
7. Cite source files or graph evidence and label uncertain inferences.

The skill references must describe:

- MCP tools and resources;
- Rust extraction command boundaries;
- C# extraction command boundaries;
- local testbeds as optional prior art only;
- custom-agent handoff guidance;
- troubleshooting for missing database, stale routes, and unavailable MCP
  server.

## Custom-Agent Contract

Generate only these project-scoped Codex custom-agent templates:

- `semantic-graph-explorer`;
- `semantic-graph-route-verifier`;
- `semantic-graph-rust-refresh`;
- `semantic-graph-csharp-refresh`;
- `semantic-graph-plan-auditor`.

Each generated TOML file must include:

```toml
name = "semantic-graph-explorer"
description = "Use SemanticGraph MCP tools to answer code relationship questions with graph evidence."
developer_instructions = """
...
"""
```

Agent handoff text must require the caller to provide:

- database path or configured MCP server context;
- workspace root when refresh commands are allowed;
- whether mutation is allowed;
- exact MCP tools or CLI commands the agent may use.

Agent instructions must enforce:

- read-only agents do not run extraction commands;
- refresh agents report command, route selectors, summary counts, and
  validation performed;
- plan/audit outputs use `Confirmed`, `Inferred`, `Unknown`, and `Validation`
  sections when precision matters;
- no agent relies on temporary chunk files unless its generated host variant
  explicitly defines that mechanism.

Do not generate a smoke-test custom agent.

## Generator Command Contract

`semantic-graph-agent-assets generate` should:

- load `agent-assets/manifest.toml`;
- load only manifest-referenced fragments;
- render the expected Codex artifact tree deterministically;
- create parent directories under `agent-assets/expected/codex/`;
- remove stale generated files under the expected Codex tree only when they
  are no longer declared by the manifest;
- print created, updated, unchanged, and removed expected-artifact paths;
- avoid writing anywhere outside `agent-assets/expected/`.

`semantic-graph-agent-assets check` should:

- load the same manifest and fragments;
- render into a temporary directory;
- compare rendered output against `agent-assets/expected/codex/`;
- fail with a concise diff-oriented path report when artifacts drift;
- pass with no filesystem changes when expected artifacts match.

Both commands should return typed errors and stable nonzero exit codes for:

- invalid manifest TOML;
- missing fragment files;
- duplicate output paths;
- output paths that escape the expected-artifact root;
- stale expected files;
- generated content drift.

## Implementation Guidance

Keep modules small and follow repository Rust style: one primary type per file,
explicit `crate::...` imports, no `super` imports, and no glob imports.

Suggested crate shape:

```text
crates/semantic-graph-agent-assets/src/lib.rs
crates/semantic-graph-agent-assets/src/main.rs
crates/semantic-graph-agent-assets/src/args/mod.rs
crates/semantic-graph-agent-assets/src/args/agent_assets_args.rs
crates/semantic-graph-agent-assets/src/error/mod.rs
crates/semantic-graph-agent-assets/src/error/agent_assets_error.rs
crates/semantic-graph-agent-assets/src/error/result.rs
crates/semantic-graph-agent-assets/src/manifest/mod.rs
crates/semantic-graph-agent-assets/src/manifest/asset_manifest.rs
crates/semantic-graph-agent-assets/src/render/mod.rs
crates/semantic-graph-agent-assets/src/render/rendered_asset.rs
crates/semantic-graph-agent-assets/src/render/asset_renderer.rs
crates/semantic-graph-agent-assets/src/files/mod.rs
crates/semantic-graph-agent-assets/src/files/asset_writer.rs
crates/semantic-graph-agent-assets/src/files/drift_checker.rs
```

Prefer structured TOML serialization for generated custom-agent files and MCP
config snippets. Avoid ad hoc string concatenation for TOML except for literal
multiline instruction bodies that are inserted as typed string values before
serialization.

Markdown generation can be template based, but keep templates explicit and
covered by snapshot or fixture tests. Generated Markdown must have stable
headings and deterministic ordering.

## Drift And Compatibility Checks

Add tests or checker rules that fail when:

- the generated skill omits required frontmatter or trigger guidance;
- generated references mention stale MCP tool names;
- generated references omit any Phase 2 read-only MCP tool;
- generated references omit any Phase 2 MCP resource;
- generated MCP config does not use `[mcp_servers.semantic_graph]`;
- generated MCP config includes mutating extraction args;
- custom-agent TOML files omit `name`, `description`, or
  `developer_instructions`;
- a smoke-test custom agent appears in generated output;
- shared fragments mention Claude-only chunk files or incompatible handoffs;
- local testbed references describe the visualizer as a durable product
  boundary.

The check command should be suitable for CI and local pre-commit use.

## Test Plan

Add tests under `crates/semantic-graph-agent-assets`.

Unit tests:

- manifest parsing accepts the checked-in manifest;
- manifest parsing rejects duplicate output paths;
- output path validation rejects absolute paths and `..` escapes;
- fragment loading rejects missing declared fragments;
- renderer emits every declared expected artifact;
- custom-agent TOML parses and contains required fields;
- MCP config snippet parses and contains `[mcp_servers.semantic_graph]`;
- generated skill contains expected trigger guidance and references;
- generated references list all Phase 2 read-only tools and resources;
- generated assets do not include a smoke-test custom agent;
- generated Codex text does not mention incompatible chunk-file handoffs.

Integration tests:

- `generate` writes the expected artifact tree in a temporary copy;
- `check` passes against matching generated expected artifacts;
- `check` fails when one expected file is changed;
- `check` fails when an expected file is missing;
- `check` fails when an extra stale expected file exists;
- `generate` refuses output paths outside `agent-assets/expected/`.

Keep tests deterministic and avoid reading or writing user-global locations.

## Implementation Sequence

1. Add `crates/semantic-graph-agent-assets` and workspace dependency wiring.
2. Add typed errors, CLI parsing, manifest models, and output path validation.
3. Add `agent-assets/manifest.toml` with the Codex host variant, skill
   references, custom-agent names, and MCP config snippet metadata.
4. Add common, Codex, and agent fragments.
5. Implement deterministic rendering for the skill and reference Markdown
   files.
6. Implement deterministic rendering for custom-agent TOML files.
7. Implement deterministic rendering for `config.semantic-graph.toml` and
   `.codex/semantic-graph/README.md`.
8. Implement `generate` for the checked-in expected Codex tree.
9. Implement `check` with temporary rendering and drift reporting.
10. Add unit and integration tests for manifest validation, rendering, drift
    checks, and host handoff guardrails.
11. Run validation and clean up every warning before presenting Phase 3 as
    complete.

Keep patches narrow enough that failures identify either manifest parsing,
rendering, file output, or drift checking.

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| Phase 3 expands into installer behavior. | Keep generated output under `agent-assets/expected/` only and defer project writes to the later installer plan. |
| Generated Codex assets drift from MCP server tool names. | Add checker tests that compare generated tool/resource references against the Phase 2 MCP registry or a single local expected list sourced from it. |
| Host-specific instructions leak into shared fragments. | Split common and Codex fragments, and add tests for incompatible handoff phrases. |
| The generator overwrites user files. | Phase 3 never writes to `.agents/`, `.codex/`, `$HOME`, or `/etc`; only the expected-artifact tree is writable. |
| TOML output becomes hard to merge later. | Generate structured TOML deterministically and keep `.codex/config.toml` merge policy out of Phase 3. |
| Visualizer language becomes product guidance. | Generated local-testbed references must state that visualizer surfaces are prior art and optional local smoke surfaces only. |
