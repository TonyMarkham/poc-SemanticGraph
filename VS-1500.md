# VS-1500: Phase 5 Implementation Plan For Installer Hardening

## Purpose

Define the implementation plan for Phase 5 of [VS-100.md](VS-100.md):
hardening the project-local Codex installer after the first
`semantic-graph install codex` workflow.

This plan follows the accepted decisions in [VS-1000.md](VS-1000.md). In
particular:

- Generated Codex assets remain project-local under `.agents/skills`,
  `.codex/agents`, and `.codex/semantic-graph`.
- The generated MCP config table name remains
  `[mcp_servers.semantic_graph]`.
- Existing SemanticGraph database config compatibility through
  `.refactor-radar/config.toml` must be preserved.
- The Blazor visualizer and JSON-RPC backend remain local testbeds only and
  must not define installer hardening behavior.
- Mutating extraction MCP tools remain later work and must not be enabled by
  installer hardening.
- No smoke-test custom agent is generated or installed.

## Phase Boundary

[VS-100.md](VS-100.md) contains an older broad Phase 5 label for documentation
and a later granular implementation breakdown. [VS-1300.md](VS-1300.md) and
[VS-1400.md](VS-1400.md) already use the granular breakdown, so this plan uses
that same boundary:

```text
Phase 5: Installer hardening
```

The Phase 5 merge gate from [VS-100.md](VS-100.md) is:

```text
Reinstall, --dry-run, --force, uninstall, and preservation of unrelated Codex
config are tested.
```

Documentation and end-to-end smoke coverage remain Phase 8 work. `doctor
codex` remains Phase 6 work. Optional extraction MCP tools remain Phase 7 work.

## Goal

Harden `crates/semantic-graph-cli` so the Codex installer is safe for repeated
use in an existing project and add a safe uninstall workflow:

```sh
semantic-graph install codex
semantic-graph uninstall codex
```

Phase 4 already provides the first install workflow, basic `--dry-run`,
`--force`, manifest writing, config merge, and simple reinstall behavior.
Phase 5 should make those behaviors durable enough for real project-local use:

- reinstall is idempotent and manifest-aware;
- asset updates are allowed only when ownership is proven by the manifest or
  explicitly forced;
- stale files that are no longer generated are handled deliberately;
- `.codex/config.toml` preserves unrelated user content during reinstall and
  uninstall;
- uninstall removes only manifest-managed resources and managed config fields;
- every create, update, skip, delete, and refusal is reported;
- all hardening behavior is covered by temporary-project tests.

- Do not add optional extraction MCP tools.

- Do not modify `AGENTS.md`.

- Do not generate or install a smoke-test custom agent.

## Crate Ownership

`semantic-graph-cli` should own:

- top-level parsing for `semantic-graph uninstall codex`;
- reinstall planning against the existing install manifest;
- stale managed-file detection;
- manifest-owned update decisions;
- uninstall planning;
- uninstall reporting;
- config removal or update for managed SemanticGraph MCP fields;
- checksum verification for managed files;
- refusal of modified managed files unless `--force` is passed;
- path validation for every manifest entry before any read or write;
- tests for reinstall, uninstall, stale-file handling, and config
  preservation.

`semantic-graph-cli` should not own:

- skill, reference, custom-agent, README, or MCP snippet prose generation;
- MCP protocol handling;
- graph database queries;
- graph extraction or refresh orchestration;
- `doctor codex` diagnosis;
- user-global Codex setup.

## CLI Contract

Existing command:

```sh
semantic-graph install codex \
  --project . \
  --database-path .local/rust-workspace-extract.db \
  --mcp read-only \
  --dry-run \
  --force
```

New command:

```sh
semantic-graph uninstall codex \
  --project . \
  --dry-run \
  --force
```

Rules:

- `--project` defaults to the current working directory.
- `uninstall codex` requires a parseable
  `.codex/semantic-graph/install-manifest.json`.
- `uninstall codex --dry-run` reports the uninstall plan without writing or
  deleting files.
- `uninstall codex` removes only manifest-managed generated files whose current
  checksum matches the manifest.
- `uninstall codex` refuses to remove a manifest-managed generated file whose
  current checksum differs from the manifest unless `--force` is passed.
- `--force` applies only to paths recorded in the SemanticGraph install
  manifest and to managed fields in `[mcp_servers.semantic_graph]`.
- Missing manifest-managed files are reported as skipped or missing, not as
  fatal errors.
- Invalid manifest paths, absolute paths, `..` escapes, and symlink escapes are
  fatal before any file operation.
- Unsupported commands such as `doctor codex` continue to fail with normal clap
  errors until Phase 6.
- Extraction-related flags and modes remain unavailable.

## Reinstall Contract

Reinstall planning should compare three inputs:

1. The current Phase 3 rendered Codex assets.
2. The selected project's existing files.
3. The existing SemanticGraph install manifest, when present.

For generated files other than `.codex/config.toml`:

- create files that do not exist;
- skip files that already match the newly rendered content;
- update files whose existing checksum matches the manifest checksum;
- refuse files whose existing checksum differs from the manifest checksum
  unless `--force` is passed;
- remove or report stale manifest-managed files that are no longer part of the
  current rendered asset set;
- never update a path that is not project-relative and validated.

For `.codex/config.toml`:

- parse and serialize TOML structurally;
- preserve unrelated top-level keys;
- preserve unrelated MCP server tables;
- preserve unrelated comments where the current merger can do so;
- replace only managed SemanticGraph MCP fields during install;
- preserve unrelated keys inside `[mcp_servers.semantic_graph]` when possible;
- keep `--database-path` behavior from Phase 4;
- keep `--mcp disabled` behavior from Phase 4;
- never add `--enable-extract-tools`.

Reinstall should update
`.codex/semantic-graph/install-manifest.json` only after every other write has
succeeded. The final manifest must describe the files that remain managed after
the reinstall, not stale files that were removed.

## Uninstall Contract

Uninstall is manifest-led. It should not scan for likely SemanticGraph files
when the manifest is missing.

For manifest-managed generated files:

- delete the file when it exists and its checksum matches the manifest;
- skip the file when it is already missing;
- refuse the file when it exists but its checksum differs from the manifest;
- with `--force`, delete only the manifest-listed file path after path
  validation.

For `.codex/config.toml`:

- remove the managed fields from `[mcp_servers.semantic_graph]`;
- remove the `semantic_graph` MCP table only when no unrelated keys remain;
- remove the parent `mcp_servers` table only when it becomes empty and the TOML
  representation supports doing so cleanly;
- delete `.codex/config.toml` only when no unrelated content remains after
  removing managed SemanticGraph config;
- refuse to modify an unparsable config file because unrelated content cannot
  be preserved safely.

For `.codex/semantic-graph/install-manifest.json`:

- delete the manifest last, after all other planned deletes and config updates
  succeed;
- include the manifest delete in dry-run and real reports;
- keep the manifest if any refusal prevents uninstall from completing.

Directory cleanup should be conservative:

- remove known SemanticGraph-owned directories only when they are empty after
  file removal;
- never remove `.codex`, `.codex/agents`, `.agents`, or `.agents/skills` if
  they contain any non-empty or unrelated content;
- report directory cleanup separately if implemented.

## Manifest Hardening

Keep the manifest deterministic and machine-readable. Phase 5 may keep schema
version 1 if the existing model is enough. If uninstall or stale-file handling
requires additional fields, introduce schema version 2 with explicit
backward-compatible parsing for schema version 1.

Required manifest behavior:

- reject unsupported schema versions with a clear error;
- reject manifests not created by `semantic-graph-cli`;
- reject duplicate managed file paths;
- reject absolute, empty, normalized-empty, or escaping paths;
- reject manifest entries that point outside the selected project after
  canonical validation;
- reject malformed checksums;
- sort managed entries deterministically;
- keep secret values out of the manifest.

The database path recorded by Phase 4 remains acceptable manifest metadata, but
Phase 5 must not record environment variable values, tokens, or arbitrary MCP
arguments.

## Reporting Contract

Install and uninstall reports should use the same shape where practical.

Report every planned action:

- `created`;
- `updated`;
- `deleted`;
- `skipped`;
- `missing`;
- `refused`;
- optional `removed-dir` if empty directory cleanup is implemented.

For dry-run output:

- make it explicit that no files were written or deleted;
- print the same path-level action plan as a real run;
- return success only when the real run would not refuse any file.

For refusal output:

- include every refused path;
- state whether the refusal is due to checksum mismatch, invalid manifest,
  invalid path, TOML parse failure, or project escape;
- do not perform partial writes after a refusal is known.

## Rust Implementation Guidance

Keep modules small and follow repository style:

- exactly one Rust type definition per file;
- explicit `crate::...` imports;
- no `super` imports;
- no glob imports;
- no `anyhow`;
- no direct `std::result::Result` return values outside custom result aliases
  in error modules.

Suggested additions:

```text
crates/semantic-graph-cli/src/args/uninstall_args.rs
crates/semantic-graph-cli/src/args/uninstall_command.rs
crates/semantic-graph-cli/src/args/codex_uninstall_args.rs
crates/semantic-graph-cli/src/install/codex_uninstaller.rs
crates/semantic-graph-cli/src/install/codex_uninstall_plan.rs
crates/semantic-graph-cli/src/install/codex_uninstall_report.rs
crates/semantic-graph-cli/src/install/uninstall_manifest_reader.rs

crates/semantic-graph-cli/src/install/directory_cleanup.rs
crates/semantic-graph-cli/src/codex_config/codex_config_uninstaller.rs
```

If a suggested file naturally needs multiple Rust types, split it further
instead of relaxing the one-type-per-file rule.

Use the existing crate-local result alias:

```rust
pub type SemanticGraphCliResult<T> = Result<T, SemanticGraphCliError>;
```

Keep that alias in the error module. Do not write public or private functions
that return `std::result::Result<..., ...>` directly.

## Error Handling

Follow the repository's typed error style:

- use `thiserror`;
- use `error-location`;
- preserve `SemanticGraphCliError` and `SemanticGraphCliResult<T>`;
- provide `#[track_caller]` constructors where useful;
- preserve source errors for IO, TOML, JSON, checksum, and asset rendering
  failures;
- add clear variants for missing manifest, unsupported manifest schema,
  malformed manifest entry, checksum mismatch refusal, stale-file refusal,
  config parse refusal, and uninstall refusal.

The CLI should exit nonzero for refused writes, refused deletes, invalid
arguments, invalid paths, config parse failures, manifest parse failures,
manifest write failures, and asset rendering failures.

## Implementation Sequence

1. Extend CLI parsing with `semantic-graph uninstall codex`, `--project`,
   `--dry-run`, and `--force`.
2. Add typed uninstall errors and report variants without changing install
   behavior.
3. Harden manifest loading with schema, crate, duplicate path, checksum, and
   path validation.
4. Refactor shared file-action planning so install and uninstall can report
   create, update, delete, skip, missing, and refusal actions consistently.
5. Harden reinstall planning against manifest checksums and stale
   manifest-managed files.
6. Add config uninstall behavior that removes managed SemanticGraph MCP fields
   while preserving unrelated config.
7. Implement uninstall planning without writes.
8. Implement uninstall dry-run output.
9. Implement uninstall writes and deletes with the manifest deleted last.
10. Add conservative empty-directory cleanup only if it stays simple and well
    tested.
11. Add unit tests for manifest hardening, reinstall planning, config
    uninstall, and uninstall planning.
12. Add temporary-project integration tests for reinstall, dry-run, force,
    uninstall, and config preservation.
13. Run validation and remove every warning before presenting Phase 5 as
    complete.

Keep patches narrow enough that failures identify either CLI parsing, manifest
validation, reinstall planning, config merge/removal, uninstall planning, or

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| Uninstall deletes user-authored files. | Drive uninstall from the manifest, validate every path, require checksum matches by default, and make `--force` apply only to manifest-listed paths. |
| Uninstall corrupts unrelated Codex config. | Remove only managed SemanticGraph MCP fields, preserve unrelated TOML content, and refuse unparsable TOML. |
| Reinstall overwrites user edits. | Compare current bytes to manifest checksums and refuse modified managed files unless `--force` is passed. |
| Stale generated files accumulate after asset changes. | Compare manifest entries to the current generated asset set and delete or report stale managed files only when ownership is proven. |
| Manifest repair expands into `doctor codex`. | Fail clearly on invalid manifests and leave repair diagnosis to Phase 6. |
| Mutating MCP tools are enabled accidentally. | Keep `--mcp extract` and `--enable-extract-tools` unavailable and test installed config never contains extractor flags. |
| Rust style cleanup becomes expensive late in the phase. | Keep one type per file from the first patch and run focused `cargo check` and `cargo clippy` early. |
