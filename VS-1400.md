# VS-1400: Phase 4 Implementation Plan For `semantic-graph install codex`

## Purpose

Define the implementation plan for Phase 4 of [VS-100.md](VS-100.md):
creating the first polished project-local Codex installer workflow for
SemanticGraph.

This plan follows the accepted decisions in [VS-1000.md](VS-1000.md). In
particular:

- Generated Codex assets are project-local and use `.agents/skills`,
  `.codex/agents`, and Codex project config paths.
- The generated MCP config table name is `[mcp_servers.semantic_graph]`.
- The installer must preserve existing SemanticGraph database config
  compatibility and must not rename or migrate `.refactor-radar/config.toml`.
- The current Blazor/JSON-RPC visualizer remains only a local testbed and must
  not define installer behavior.
- Mutating extraction MCP tools are later work and must remain disabled unless
  explicitly gated.

## Phase Boundary

`VS-100.md` contains an earlier broad Phase 4 label for optional extraction MCP
tools and a later granular implementation breakdown. This plan uses the
granular Phase 4 boundary already adopted by [VS-1300.md](VS-1300.md):

```text
Phase 4: semantic-graph install codex
```

Optional extraction MCP tools remain later work. Installer hardening beyond the
first fresh-install workflow, `semantic-graph uninstall codex`, and
`semantic-graph doctor codex` remain follow-on phases.

## Goal

Add a new workspace crate:

```text
crates/semantic-graph-cli
```

The crate owns the user-facing `semantic-graph` binary and implements:

```sh
semantic-graph install codex
```

The Phase 4 installer writes repo-local Codex resources into the selected
project:

| Path | Purpose |
| --- | --- |
| `.agents/skills/semantic-graph/SKILL.md` | Repo-scoped Codex skill. |
| `.agents/skills/semantic-graph/references/*.md` | Progressive reference files for the skill. |
| `.codex/agents/*.toml` | Project-scoped Codex custom agents generated in Phase 3. |
| `.codex/config.toml` | Project-scoped Codex config structurally merged with the SemanticGraph MCP server table. |
| `.codex/semantic-graph/README.md` | Local explanation of the managed resources. |
| `.codex/semantic-graph/install-manifest.json` | Managed-file manifest for future reinstall, force, and uninstall behavior. |

The first merge gate is a fresh temporary project install that writes those
resources without touching `$HOME`, `/etc`, user-global Codex configuration, or
files outside the selected project.

## Crate Ownership

`semantic-graph-cli` should own:

- top-level `semantic-graph` CLI parsing;
- the `install codex` subcommand;
- project path validation and canonicalization;
- dry-run reporting;
- install planning;
- install manifest creation;
- managed-file checksum calculation;
- atomic file writes where practical;
- structural merge of `.codex/config.toml`;
- refusal to overwrite untracked user-authored files unless `--force` is
  passed;
- user-facing install output that lists created, updated, skipped, and refused
  paths;
- tests for fresh temp-project install behavior.

`semantic-graph-cli` should not own:

- skill, reference, custom-agent, or README prose generation;
- Phase 3 drift checking;
- MCP protocol handling;
- graph database queries;
- graph extraction or refresh orchestration;
- visualizer behavior;
- user-global Codex setup.

## CLI Contract

Initial supported command:

```sh
semantic-graph install codex
```

Supported options:

```sh
semantic-graph install codex \
  --project . \
  --database-path .local/rust-workspace-extract.db \
  --mcp read-only \
  --dry-run \
  --force
```

Rules:

- `--project` defaults to the current working directory.
- `--database-path` is optional. When provided, the installer records it in the
  installed MCP config args. When omitted, the installed MCP config keeps empty
  args so `semantic-graph-mcp-server` uses existing SemanticGraph config
  discovery.
- `--mcp` supports `read-only` and `disabled` in Phase 4.
- `--mcp read-only` installs or updates `[mcp_servers.semantic_graph]` with
  `enabled = true`.
- `--mcp disabled` installs generated skill and agent assets but writes the MCP
  table with `enabled = false` or skips MCP config when that is the narrower
  implementation. Pick one behavior, document it in CLI help, and test it.
- `--dry-run` prints the install plan without writing files.
- `--force` allows replacement of conflicting project files only for paths that
  Phase 4 manages. It must not authorize writes outside the project.
- Unknown subcommands such as `doctor` and `uninstall` should fail with normal
  clap errors until their phases are implemented.
- `--mcp extract` and `--enable-extract-tools` are not available in Phase 4.

The command should print every path it would create, update, skip, or refuse.
For `--dry-run`, output must be identical in shape to a real install report but
must clearly mark that no files were written.

## Project Path Rules

The installer must:

- canonicalize `--project`;
- create only the required project-local parent directories;
- reject output paths that are absolute, contain `..`, or escape the project
  root after normalization;
- treat all generated asset output paths as project-relative paths;
- refuse to follow generated output paths into symlink escapes if canonical
  checks can detect them;
- never infer `$HOME` or user-global Codex paths.

The selected project does not need to be a Git repository in Phase 4. Tests
should use temporary directories so the installer behavior is independent of
the current workspace checkout.

## Asset Source Contract

Use Phase 3 as the source of asset content:

1. Load `agent-assets/manifest.toml`.
2. Render the Codex assets through `semantic-graph-agent-assets`.
3. Map each rendered asset's output path into the selected project.
4. Install all generated assets except `.codex/config.semantic-graph.toml`,
   which is an input snippet for the structural merge into `.codex/config.toml`.

Do not install `.codex/config.semantic-graph.toml` as a final project file. Its
content is merged into `.codex/config.toml`.

## Codex Config Merge Contract

The installer must update `.codex/config.toml` structurally using TOML parsing
and serialization. Do not append strings to the file.

Merge rules:

- Preserve unrelated top-level keys.
- Preserve unrelated `[mcp_servers.*]` tables.
- Create `[mcp_servers.semantic_graph]` when missing.
- Replace only the `semantic_graph` MCP table fields managed by
  SemanticGraph.
- Preserve unrelated keys inside `[mcp_servers.semantic_graph]` only if they do
  not conflict with the managed fields. If preserving unknown keys complicates
  deterministic output, document the managed-table replacement behavior and
  test it.
- Keep output deterministic.

Managed fields:

```toml
command = ".refactor-radar/bin/semantic-graph-mcp-server"
args = []
enabled = true
required = false
startup_timeout_sec = 10
tool_timeout_sec = 60
```

When `--database-path` is provided, set:

```toml
args = [
  "--database-path",
  "<provided-project-relative-or-absolute-path>",
]
```

Prefer preserving the exact user-provided database path string in config. Do
not treat the database path as a source file to read.

When `--mcp disabled` uses a disabled table, set `enabled = false` and do not
add extractor flags.

## Manifest Contract

Write `.codex/semantic-graph/install-manifest.json` after all other writes
succeed.

The manifest should be deterministic and include:

- manifest schema version;
- installer crate name and version;
- project root path as recorded at install time;
- installed mode, including `mcp` mode and optional database path;
- generated asset source, including the Phase 3 manifest path or a stable asset
  generation version string;
- managed file entries;
- each managed file's project-relative path;
- SHA-256 checksum of the final installed content;
- whether the file was created or updated during this install;
- install timestamp only if existing repo patterns already support stable time
  fields in tests. Otherwise omit timestamps for deterministic tests.

The manifest must not record secret values. The Phase 4 database path is not a
secret by itself, but do not record environment variable values or token-like
arguments.

Future uninstall and reinstall phases will rely on this manifest, so keep it
machine-readable and stable.

## File Write Safety

For each planned file:

- create parent directories explicitly;
- if the target file does not exist, write it;
- if the target file exists with identical content, skip it;
- if the target file exists and is already recorded in a SemanticGraph manifest
  with the expected checksum, update it;
- if the target file exists, differs, and is not recorded as managed, refuse it
  unless `--force` is passed;
- for `--force`, replace only the exact project-relative paths managed by this
  install plan;
- use temporary files plus atomic rename where practical;
- report every action.

Because robust reinstall hardening is Phase 5, keep Phase 4 behavior narrow and
well tested for fresh projects and simple conflicts. Do not implement broad
manifest repair or cleanup in this phase.

## Error Handling

Follow the repository's typed error style:

- use `thiserror`;
- use `error-location`;
- expose `SemanticGraphCliError` and `SemanticGraphCliResult<T>`;
- provide constructors with `#[track_caller]` where useful;
- preserve source errors for IO, TOML, JSON, and asset rendering failures;
- return clear user-facing messages for path escape, conflict, invalid project,
  invalid MCP mode, and config parse errors.

The CLI should exit nonzero for refused writes, invalid arguments, config parse
failures, manifest write failures, and asset rendering failures.

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| The installer duplicates Phase 3 asset generation. | Reuse `semantic-graph-agent-assets` rendering and manifest models; add a narrow public helper there if needed. |
| The installer overwrites user-authored Codex files. | Plan every file, compare existing content, require manifest ownership or `--force`, and test conflict refusal. |
| `.codex/config.toml` merge corrupts unrelated user config. | Parse and serialize TOML structurally, preserve unrelated keys, and test existing config cases. |
| Phase 4 expands into uninstall or doctor behavior. | Keep the CLI surface limited to `install codex`; leave repair, uninstall, and diagnosis to later plans. |
| Mutating MCP tools become enabled accidentally. | Support only read-only or disabled MCP install modes and test that generated config never includes `--enable-extract-tools`. |
| File writes escape the selected project. | Validate generated output paths before planning, canonicalize the project root, and test path escapes. |
| Rust style cleanup becomes expensive late in the phase. | Keep one type per file from the first patch and run focused `cargo check` and `cargo clippy` early. |
