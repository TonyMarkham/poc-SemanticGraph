# VS-1200: Phase 2 Implementation Plan For `semantic-graph-mcp-server`

## Purpose

Define the implementation plan for Phase 2 of [VS-100.md](VS-100.md):
creating the read-only, stdio-only MCP server for the SemanticGraph SQLite
store.

This plan follows the accepted decisions in [VS-1000.md](VS-1000.md). In
particular:

- Phase 2 consumes `crates/semantic-graph-query` from a separate
  `crates/semantic-graph-mcp-server` crate.
- The MCP server is read-only and stdio-only.
- Mutating extraction MCP tools are later work and must remain disabled unless
  explicitly gated.
- Use the `rmcp` crate as the Rust MCP SDK. Record the VS-1000 SDK adoption
  evidence for `rmcp` before finalizing its version, features, and integration
  shape.
- The current Blazor/JSON-RPC visualizer is only local testbed evidence and
  must not define the durable MCP boundary.

## Goal

Add a new workspace crate:

```text
crates/semantic-graph-mcp-server
```

The crate owns stdio MCP I/O, protocol handling, tool schemas, resource
schemas, output sanitization, and MCP-specific error mapping for a read-only
SemanticGraph server.

The default command shape is:

```sh
semantic-graph-mcp-server
```

By default, the server resolves the database path through existing
SemanticGraph configuration, preserving `.refactor-radar/config.toml`
compatibility. `--database-path` is a utility override for tests, temporary
databases, or manual launches that should bypass config discovery.

The server must expose read-only MCP tools backed by `semantic-graph-query`:

- `graph_stats`;
- `graph_search_nodes`;
- `graph_node_details`;
- `graph_edge_details`;
- `graph_projection`;
- `graph_neighbors`;
- `graph_shortest_path`;
- `graph_file_summary`;
- `graph_route_status`.

It must also expose read-only MCP resources:

- `semantic-graph://schema`;
- `semantic-graph://workspace`;
- `semantic-graph://routes`;
- `semantic-graph://local-testbeds`.

## Non-Goals

- Do not implement HTTP transport. No HTTP variant is planned.
- Do not add `--enable-extract-tools`.
- Do not expose Rust or C# extraction MCP tools.
- Do not expose arbitrary SQL, arbitrary shell commands, raw file reads, reset,
  delete, hard-prune, or stale-closing operations.
- Do not generate or install Codex skills, custom agents, `.codex/config.toml`,
  or `.agents/skills` assets.
- Do not add `semantic-graph-agent-assets` or `semantic-graph-cli`.
- Do not modify `.refactor-radar/config.toml` compatibility behavior.
- Do not update the visualizer server as part of Phase 2.
- Do not evaluate alternative MCP SDKs or implement a local MCP protocol
  fallback unless a later explicit decision reverses the `rmcp` requirement.

## Crate Ownership

`semantic-graph-mcp-server` should own:

- CLI argument parsing for the MCP server binary;
- stdio MCP I/O;
- MCP protocol request and response envelopes;
- MCP tool and resource definitions;
- MCP-specific DTOs where the protocol requires schemas distinct from
  `semantic-graph-query` models;
- mapping MCP tool input into `semantic-graph-query` request structs;
- mapping `QueryError` into MCP error responses;
- text sanitization for graph-originated strings included in transcript-facing
  text content;
- integration tests that drive the server through stdio against a fixture
  SQLite database.

`semantic-graph-mcp-server` should not own:

- durable graph SQL queries;
- SQLite schema migrations;
- graph mutation or extraction orchestration;
- database path discovery policy beyond using existing SemanticGraph config
  resolution plus an explicit `--database-path` override;
- JSON-RPC DTOs for the obsolete visualizer backend;
- Codex installer behavior;
- generated skills or custom-agent assets.

## `rmcp` Adoption Note

Use `rmcp` as the Phase 2 MCP SDK. Before finalizing its dependency version and
feature flags, record a short checked-in adoption note in this file or in a
linked follow-up decision note. The note must cover the VS-1000 evidence list:

- crate name and version;
- maintenance status;
- protocol features needed for tools and resources;
- stdio support;
- structured output support;
- error handling fit with `thiserror` and `error-location`;
- dependency impact;
- testability with fixture SQLite databases.

The adoption note is not a license to reconsider the SDK choice. Its job is to
pin the `rmcp` version, identify required features, and make integration risks
visible before implementation proceeds.

Do not implement a local MCP protocol fallback in Phase 2 unless a later
explicit decision reverses this `rmcp` requirement. The adoption work must not
add mutating tools, non-stdio transports, installer behavior, or global
configuration writes.

Adoption note for this implementation:

- Crate/version: `rmcp` `1.7.0`.
- Maintenance status: docs.rs publishes `1.7.0` as the current crate release
  with repository, homepage, owner, source, and Apache-2.0 metadata.
- Enabled features: `server`, `schemars`, and `transport-io`, with
  `default-features = false`; HTTP, OAuth, client child-process, and other
  non-stdio transport features remain disabled.
- Protocol fit: `rmcp` provides `ServerHandler`, tool listing/calls, resource
  listing/reads, `ServerCapabilities`, and MCP JSON-RPC error data.
- Stdio support: `transport-io` exposes server-side stdio transport.
- Structured output: `CallToolResult::structured` supports JSON structured
  content for each tool result.
- Error handling fit: crate-local `McpServerError` keeps startup/service errors
  typed with `thiserror` and `error-location`; per-request query errors map
  into `rmcp::ErrorData` without adding `anyhow`.
- Dependency impact: direct runtime dependency is limited to `rmcp` plus
  existing workspace crates; `schemars` is added directly for the derive macro
  used by MCP input schemas. The selected `rmcp` features avoid HTTP
  server/client stacks and mutation-oriented behavior.
- Testability: manual `ServerHandler` wiring exposes exact registries and
  request handlers that can be tested against fixture SQLite databases and at
  least one process-level stdio smoke.

## CLI Contract

Initial command:

```sh
semantic-graph-mcp-server
```

Utility override command:

```sh
semantic-graph-mcp-server --database-path .local/rust-workspace-extract.db
```

CLI rules:

- `--database-path` is optional and overrides config-based database discovery
  when provided.
- Without `--database-path`, resolve the database path with existing
  SemanticGraph config behavior, including `.refactor-radar/config.toml`
  compatibility.
- Communication is always stdio. There is no `--transport` flag.
- No `--enable-extract-tools` flag is implemented in Phase 2.
- No workspace-root argument is required because Phase 2 reads from SQLite and
  does not resolve filesystem paths for mutation.
- The server opens the database through `semantic-graph-query`, which already
  uses read-only SQLite connection setup.
- If neither config resolution nor `--database-path` yields a database path,
  fail before starting the MCP protocol and print a clear setup message.

## Protocol Contract

The server should support the smallest MCP surface required for a useful
read-only MVP:

- initialization handshake;
- tool listing;
- tool calls;
- resource listing;
- resource reads;
- structured JSON tool results;
- clear JSON-RPC error responses for invalid method, invalid params, not found,
  database, and internal errors.

The implementation should preserve enough protocol metadata for MCP-compatible
hosts to discover tool names, descriptions, and JSON input schemas.

When wiring `rmcp`, keep request handling strict:

- reject malformed JSON;
- reject missing JSON-RPC ids where the protocol requires a response;
- reject unknown tool and resource names;
- reject invalid tool arguments before calling `semantic-graph-query`;
- avoid panics on unexpected client messages.

## Tool Contracts

All tools return structured JSON content. Text content, when present, is a
short sanitized summary for agent transcripts and must not be the only source
of data.

### `graph_stats`

Purpose:

Return database-wide counts and latest extraction run metadata.

Input schema:

```json
{}
```

Backed by:

```rust
GraphQueryService::stats()
```

### `graph_search_nodes`

Purpose:

Search active nodes by name, display label, qualified name, or source path.

Input schema:

```json
{
  "query": "GraphQueryService",
  "limit": 25
}
```

Backed by:

```rust
GraphQueryService::search_nodes(NodeSearchRequest { ... })
```

### `graph_node_details`

Purpose:

Return one node with relation summaries and occurrences.

Input schema:

```json
{
  "nodeId": "node-id"
}
```

Backed by:

```rust
GraphQueryService::node_details(NodeDetailsRequest { ... })
```

### `graph_edge_details`

Purpose:

Return one edge with endpoints and edge evidence.

Input schema:

```json
{
  "edgeId": "edge-id"
}
```

Backed by:

```rust
GraphQueryService::edge_details(EdgeDetailsRequest { ... })
```

### `graph_projection`

Purpose:

Return a bounded active graph projection.

Input schema:

```json
{
  "limit": 150
}
```

Backed by:

```rust
GraphQueryService::projection(ProjectionRequest { ... })
```

### `graph_neighbors`

Purpose:

Return bounded incoming and outgoing active neighbors for one node.

Input schema:

```json
{
  "nodeId": "node-id",
  "direction": "both",
  "relation": "CALLS",
  "limit": 25
}
```

Backed by:

```rust
GraphQueryService::neighbors(NeighborsRequest { ... })
```

`direction` must map to the existing `NeighborDirection` model. Accept only the
values supported by `semantic-graph-query`.

### `graph_shortest_path`

Purpose:

Return a bounded active path between two node ids.

Input schema:

```json
{
  "sourceNodeId": "source-node-id",
  "targetNodeId": "target-node-id",
  "maxDepth": 6,
  "maxVisitedNodes": 500
}
```

Backed by:

```rust
GraphQueryService::shortest_path(ShortestPathRequest { ... })
```

No path found is a successful result with `found: false`, matching the query
crate contract.

### `graph_file_summary`

Purpose:

Return the file row, file node, contained symbols, touching edges, and route
freshness for one file path already known to the database.

Input schema:

```json
{
  "filePath": "crates/wip/src/lib.rs",
  "workspaceId": 1,
  "rootUri": "file:///workspace",
  "edgeLimit": 50
}
```

Backed by:

```rust
GraphQueryService::file_summary(FileSummaryRequest { ... })
```

The `filePath` argument is a database `files.path` value. The MCP server must
not read the file from disk.

### `graph_route_status`

Purpose:

Return route freshness rows filtered by workspace, route, scope, scope key, or
file path.

Input schema:

```json
{
  "workspaceId": 1,
  "rootUri": "file:///workspace",
  "route": "rust.workspace.calls",
  "scope": "file",
  "scopeKey": "crates/wip/src/lib.rs",
  "filePath": "crates/wip/src/lib.rs",
  "limit": 50
}
```

Backed by:

```rust
GraphQueryService::route_status(RouteStatusRequest { ... })
```

## Resource Contracts

Resources are read-only and deterministic.

### `semantic-graph://schema`

Return a compact human-readable schema summary for the graph tables the tools
query:

- `workspaces`;
- `extraction_runs`;
- `files`;
- `nodes`;
- `edges`;
- `occurrences`;
- `edge_evidence`;
- `extraction_route_status`;
- `route_observations`.

This resource should be static text maintained with the MCP server, not a raw
SQLite schema dump.

### `semantic-graph://workspace`

Return current server context:

- database path;
- stdio-only mode;
- read-only mode;
- workspace count;
- latest extraction run summaries when available.

This resource may call `GraphQueryService::stats()`.

### `semantic-graph://routes`

Return route names and freshness semantics used by the extractor. Keep this
resource aligned with route names currently recorded by the Rust and C# route
surfaces.

Use local code and README evidence for route names; do not invent route names
from Graphify or agent plans.

### `semantic-graph://local-testbeds`

Return optional local testbed notes for this repository:

- `apps/SemanticGraph.Visualizer`;
- `crates/semantic-graph-visualizer-server`.

The resource must state that these are local testbeds and prior art, not the
durable MCP or query boundary.

## Output Rules

- Never return more rows than the requested limit or the server-side query
  limit.
- Preserve node ids and edge ids in structured output.
- Preserve occurrence ids and edge evidence ids where the query model provides
  them.
- Preserve `valid_to_run_id` and stale state in structured output.
- Prefer JSON object content over prose.
- Keep transcript-facing text short and sanitized.
- Do not truncate structured JSON fields silently; rely on query limits before
  serialization.
- Do not expose raw SQL errors to users beyond a stable database-error message.

## Sanitization

Add one shared helper for graph-originated strings embedded in text content.

The helper should:

- replace ASCII control characters except tab, newline, and carriage return;
- cap text-summary field lengths;
- avoid changing structured JSON fields that are intended to preserve exact
  graph values;
- be covered by unit tests.

Use this helper for tool summaries and resource prose. Structured tool data can
preserve exact values because it is not meant to be parsed from transcript
text.

## Error Handling

Follow the repository's typed error style:

- use `thiserror`;
- use `error-location`;
- do not add `anyhow`;
- expose `McpServerError` and `McpServerResult<T>`;
- provide constructors with `#[track_caller]` where useful.

Map query errors consistently:

| Query Error | MCP/JSON-RPC Mapping |
| --- | --- |
| `InvalidParams` | invalid params |
| `NotFound` | tool error result or not-found error, depending on `rmcp` convention |
| `Database` | database/internal error with sanitized message |
| `Json` | internal error with sanitized message |

The exact numeric JSON-RPC codes should follow `rmcp` conventions while keeping
stable handling for parse error, invalid request, method not found, invalid
params, and internal error cases.

## Implementation Sequence

1. Record the `rmcp` adoption note with version, feature flags, required
   protocol support, error handling fit, dependency impact, and fixture-test
   approach.
2. Add `crates/semantic-graph-mcp-server` and workspace dependency wiring.
3. Add CLI parsing for optional `--database-path`; stdio is implicit and not
   user-selectable.
4. Add typed `McpServerError`, `McpServerResult`, and query-error mapping.
5. Add database path resolution that uses existing SemanticGraph config by
   default and treats `--database-path` as an override.
6. Add server state that constructs `GraphQueryService` from the resolved
   database path.
7. Add stdio protocol handshake, tool listing, resource listing, tool calls,
   and resource reads.
8. Add tool schemas and handlers for `graph_stats`, `graph_search_nodes`,
   `graph_node_details`, and `graph_edge_details`.
9. Add tool schemas and handlers for `graph_projection`, `graph_neighbors`,
   `graph_shortest_path`, `graph_file_summary`, and `graph_route_status`.
10. Add static resource handlers for schema, routes, and local testbeds.
11. Add workspace resource handling backed by `GraphQueryService::stats()`.
12. Add shared transcript sanitization and apply it to text summaries and
    resource prose.
13. Add fixture-backed MCP integration tests over stdio.
14. Add README examples for starting the stdio server from config, starting it
    with a `--database-path` override, and registering it with an
    MCP-compatible host, using `[mcp_servers.semantic_graph]` as the Codex

    complete.

Keep each patch narrow enough that failures identify one protocol, tool, or
resource surface at a time.

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| `rmcp` integration pulls in broader behavior than the read-only stdio server needs. | Keep the feature set minimal, document the dependency impact in the adoption note, and avoid enabling non-stdio or mutating capabilities in Phase 2. |
| MCP DTOs leak into the query crate. | Keep MCP-specific schemas in `semantic-graph-mcp-server` and map into `semantic-graph-query` request models at handler boundaries. |
| The server accidentally gains write capability. | Keep Phase 2 read-only, omit extraction flags, and rely on `semantic-graph-query` read-only SQLite access. |
| Tool outputs become prose-first and hard for agents to use. | Return structured JSON content for every tool and keep text summaries short. |
| Route names drift from extractor behavior. | Source route names from local extractor code and tests before writing `semantic-graph://routes`. |
| Stdio tests become brittle. | Use fixture databases with deterministic data and keep one process-level stdio smoke even if most protocol tests run in process. |
