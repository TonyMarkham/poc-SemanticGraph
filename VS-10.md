# VS-10: Route Freshness And Rust References

Status: Draft implementation plan
Date: 2026-06-14

## Goal

Add the first production semantic relation family beyond `contains`: Rust
`references` edges backed by the pinned in-process `rust-analyzer` analysis
facade.

This plan also adds route freshness and stale closing, because relation-rich
edges are not durable unless the database can say which route observed them,
which route is current, and which previously current rows are now stale.

The intended end state is:

- document-symbol extraction remains the source of canonical Rust symbol nodes;
- reference extraction resolves symbol references through `rust-analyzer`;
- canonical `references` edges are written to `edges`;
- raw provider proof is written to `edge_evidence` and `occurrences`;
- route status records whether document symbols and references are current;
- stale nodes and edges are soft-closed with `valid_to_run_id`;
- the existing visualizer can inspect reference edges and evidence without a
  custom UI rewrite.

## Non-Goals

- Do not add call edges in this plan. Calls are VS-20.
- Do not add C# reference extraction.
- Do not replace SQLite or move canonical graph truth into CSV or JSON.
- Do not shell out to a `rust-analyzer` process, LSIF output, or CLI route.
  Use the checked-in `rust-analyzer` crates through
  `crates/rust-analyzer-lib`.
- Do not add graph algorithms, centrality, communities, ranking, or projection
  persistence.
- Do not add app-owned JavaScript.
- Do not attempt complete Rust symbol identity redesign unless the source spike
  finds a cheap provider-backed identity that can be adopted without broad
  migration.

## Current Evidence

The current store already has the core canonical/proof split:

- `crates/semantic-graph-store/migrations/01_create_graph_store.sql` defines
  `nodes`, `edges`, `occurrences`, `edge_evidence`, and `extraction_runs`.
- `nodes.valid_to_run_id` and `edges.valid_to_run_id` already exist.
- `edges` already stores `relation`, `context`, `confidence`,
  `confidence_score`, `weight`, and `properties_json`.
- `edge_evidence` already stores provider, LSP method, source file, range, and
  raw JSON proof.
- `occurrences.role` already allows `reference`.

The current extractor route is intentionally narrow:

- `crates/semantic-graph-extract/src/main.rs` exposes document-symbol commands.
- `crates/semantic-graph-extract/src/persist/extraction_persister.rs` writes
  file nodes, symbol nodes, `definition` occurrences, `contains` edges, and
  `textDocument/documentSymbol` evidence.
- No production route writes `references`.
- No production route closes stale rows.

The current Rust facade is also narrow:

- `crates/rust-analyzer-lib/src/semantic/document_symbols_for_file.rs` loads the
  pinned Rust workspace and calls `analysis.file_structure`.
- `crates/rust-analyzer-lib/src/semantic/mod.rs` exports only document-symbol
  helpers.
- The pinned `rust-analyzer` submodule has a references handler backed by
  `analysis.find_all_refs`, but this repo has not wrapped that API yet.

The current visualizer is mostly ready for richer edges:

- `graph.projection`, `graph.node_details`, and `graph.edge_details` already
  filter canonical stale rows and return relation/evidence data.
- The Blazor diagram builder already has styling branches for `references`.

## Design Summary

VS-10 should make freshness explicit before adding references. The route
freshness layer should not be a JSON convention hidden inside existing rows.
It needs first-class store methods and tests.

Use two new concepts:

1. Route status: whether a route has been started, completed, or failed for a
   specific scope.
2. Route observations: which canonical node or edge IDs were observed by a
   route in a run.

The route status table answers "is this extraction route current?" The route
observation table answers "which rows does this route own strongly enough to
close when they disappear?"

## Route Model

Add route names as typed constants in the extractor/store boundary:

```text
rust.document_symbols
rust.references
```

Route names must be stable, lower-case, and persisted exactly. Do not derive
them from command names.

Use two route scopes:

```text
file
workspace
```

`rust.document_symbols` is file-scoped because one source file produces one
document-symbol tree.

`rust.references` should be workspace-scoped for VS-10. A reference query for a
symbol defined in one file can return references from many other files, and a
change in any source file can add or remove references to symbols defined
elsewhere. Treating references as only file-fresh would be incorrect for stale
closing.

## Schema Changes

Add a migration after `01_create_graph_store.sql`.

### extraction_route_status

```sql
CREATE TABLE extraction_route_status (
  id INTEGER PRIMARY KEY,
  workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
  route TEXT NOT NULL,
  scope TEXT NOT NULL CHECK (scope IN ('file', 'workspace')),
  scope_key TEXT NOT NULL,
  file_id INTEGER REFERENCES files(id),
  provider TEXT NOT NULL,
  provider_version TEXT,
  content_hash TEXT,
  last_started_run_id INTEGER REFERENCES extraction_runs(id),
  last_complete_run_id INTEGER REFERENCES extraction_runs(id),
  last_status TEXT NOT NULL CHECK (last_status IN ('running', 'complete', 'failed')),
  diagnostics_json TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(diagnostics_json)),
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (workspace_id, route, scope, scope_key, provider)
);
```

Rules:

- `scope_key` is the file URI or relative path for file-scoped routes.
- `scope_key` is the workspace root URI for workspace-scoped routes.
- `file_id` is set for file-scoped routes and `NULL` for workspace-scoped
  routes.
- `content_hash` is the file content hash for file-scoped routes.
- For workspace-scoped routes, `content_hash` is a deterministic workspace
  fingerprint built from the discovered source-file paths and content hashes.
- Failed routes update status and diagnostics but must not close stale rows.

### route_observations

```sql
CREATE TABLE route_observations (
  id INTEGER PRIMARY KEY,
  workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
  run_id INTEGER NOT NULL REFERENCES extraction_runs(id),
  route TEXT NOT NULL,
  scope TEXT NOT NULL CHECK (scope IN ('file', 'workspace')),
  scope_key TEXT NOT NULL,
  provider TEXT NOT NULL,
  entity_kind TEXT NOT NULL CHECK (entity_kind IN ('node', 'edge')),
  entity_id TEXT NOT NULL,
  source_file_id INTEGER REFERENCES files(id),
  properties_json TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(properties_json)),
  UNIQUE (
    run_id,
    route,
    scope,
    scope_key,
    provider,
    entity_kind,
    entity_id,
    source_file_id
  )
);
```

Rules:

- Observations are not source proof. They are the current-state index used for
  stale closing.
- `source_file_id` is the file that caused the observation when that is known.
  For reference edges, this is the file containing the reference occurrence.
- Keep `edge_evidence` as the detailed proof table. Do not overload it as the
  route freshness index.

Recommended indexes:

```sql
CREATE INDEX idx_extraction_route_status_workspace_route
  ON extraction_route_status(workspace_id, route, scope, scope_key);

CREATE INDEX idx_route_observations_route_run
  ON route_observations(workspace_id, route, run_id, entity_kind);

CREATE INDEX idx_route_observations_entity
  ON route_observations(entity_kind, entity_id);
```

## Store API

Add explicit store methods rather than ad hoc SQL in the extractor.

Suggested methods:

```text
start_route_status(input) -> route_status_id
complete_route_status(input) -> ()
fail_route_status(input) -> ()
record_route_observation(input) -> ()
close_stale_nodes_for_route(input) -> closed_count
close_stale_edges_for_route(input) -> closed_count
```

Implementation rules:

- `start_route_status` records `last_started_run_id` and `last_status =
  'running'`.
- `complete_route_status` records `last_complete_run_id`, status `complete`,
  diagnostics, provider version, and content hash/fingerprint.
- `fail_route_status` records status `failed` and diagnostics.
- Closing is only allowed after a route completes successfully.
- Closing updates `valid_to_run_id` only when it is currently `NULL`.
- Closing never deletes nodes, edges, evidence, or occurrences.
- Re-observing a row through `upsert_node` or `upsert_edge` must continue to set
  `valid_to_run_id = NULL`.

Do not make route freshness a global "latest run wins" rule. Different routes
will mature at different times.

## Stale Closing Policy

### Document Symbols

For a completed `rust.document_symbols` file route:

- record route observations for the file node;
- record route observations for every symbol node in that file;
- record route observations for every `contains` edge produced from that file;
- close previous `rust.document_symbols` node observations for the same file
  that were not observed in the current run;
- close previous `rust.document_symbols` `contains` edge observations for the
  same file that were not observed in the current run.

This makes the existing route durable before references depend on it.

### References

For a completed `rust.references` workspace route:

- record route observations for each canonical `references` edge;
- close previous `rust.references` edge observations in the workspace that were
  not observed in the current run;
- do not close nodes from the reference route, because references depend on
  document-symbol ownership for canonical symbols.

This is intentionally workspace-scoped in VS-10. Per-file incremental reference
freshness can come later, after the repo has a reliable dependency model for
which source files can affect a reference query.

## Reference Semantics

Persist references as directed edges:

```text
source node --references--> target node
```

Definitions:

- Target node: the canonical symbol being referenced.
- Source node: the innermost current canonical symbol whose range contains the
  reference occurrence.
- Fallback source node: the file node, only when no enclosing symbol can be
  resolved.
- Occurrence: the target symbol occurring at the reference range in the source
  file.

Canonical edge fields:

```text
relation = "references"
context = "symbol"
confidence = "EXTRACTED" when source and target symbols are resolved
confidence = "AMBIGUOUS" when the source falls back to the file node
confidence_score = 1.0 for fully resolved symbol-to-symbol references
confidence_score = 0.6 for file-fallback references
weight = number of reference locations observed for this edge in the current route run
```

Evidence fields:

```text
provider = "rust-analyzer"
lsp_method = "textDocument/references"
file_id = file containing the reference occurrence
range = reference occurrence range
raw_json includes target symbol key, source symbol key or file fallback,
          provider range, route, and source resolution mode
```

Occurrence fields:

```text
node_id = target node
role = "reference"
file_id = file containing the reference occurrence
range = reference occurrence range
enclosing_node_id = source node when source is a symbol, otherwise NULL or file node policy
```

Recommendation: set `enclosing_node_id` to the source symbol when resolved.
When using the file fallback, set it to `NULL` and include the fallback details
in `raw_json`; this keeps `enclosing_node_id` semantically tied to symbol
containment rather than file containment.

## Rust Analyzer Facade Work

Add a source spike first. The spike should identify the exact local API calls in
the pinned `rust-analyzer` crates and produce a tiny facade test before broader
extractor work starts.

Expected direction from the submodule:

- references are backed by `analysis.find_all_refs`;
- the LSP handler converts results to `Location`;
- the facade should work in-process like the current document-symbol route.

Do not copy the LSP server handler wholesale. The facade should expose
provider-neutral data shaped for this repo.

Suggested new facade outputs:

```text
ResolvedReferenceSet
  target_file_path
  target_selection_range
  target_name
  references: Vec<ResolvedReferenceLocation>

ResolvedReferenceLocation
  file_path
  range
```

If the local API returns multiple declaration/reference groups for one query,
preserve enough raw shape in `raw_json` to debug it, but normalize persistence
to target node plus occurrence locations.

Reference queries should use document-symbol selection ranges as target
positions. Exclude the declaration from reference results when the API supports
that. If the provider cannot exclude declarations, filter out the target
definition range before persistence.

## Extractor Model Work

Add provider-neutral reference model types in small module files, matching the
repo's one-primary-type-per-file style.

Suggested types:

```text
ReferenceExtraction
ReferenceBatchExtraction
ExtractedReference
ReferenceOccurrence
ReferenceRouteSummary
```

A reference extraction should include:

- provider and provider version;
- workspace root URI;
- route name;
- target symbol identity;
- source occurrence file/range;
- source enclosing symbol identity when resolved;
- raw provider metadata.

Keep document symbols and references as separate route models. Do not overload
`DocumentSymbolExtraction` with optional reference data.

## Provider Work

Extend `RustAnalyzerProvider` with a reference route:

```text
extract_rust_references(request) -> ReferenceBatchExtraction
```

The request should be workspace-scoped for VS-10:

```text
ReferenceBatchRequest
  workspace_root
  package_path
  file_paths
```

Implementation order:

1. Discover Rust source files with the existing workspace discovery path.
2. Run or load document-symbol extraction for those files.
3. Build a current symbol index from canonical document-symbol nodes.
4. Query references for each eligible target symbol selection range.
5. Map each provider reference location to source file and enclosing symbol.
6. Emit reference facts grouped by canonical edge key.

Eligible target symbols for VS-10:

- functions;
- methods;
- structs;
- enums;
- enum members;
- traits/interfaces;
- fields;
- constants/statics;
- type aliases;
- modules.

Skip locals in VS-10, consistent with current `exclude_locals: true` document
symbol extraction.

## Identity And Mapping Policy

VS-10 should not pretend current identity is perfect. Current symbol keys are
range-sensitive because document symbols are derived from file/range data. That
is acceptable for this slice only if the limitation is explicit and tested.

Mapping rules:

- Target mapping uses the canonical node created from the same document-symbol
  target that seeded the reference query.
- Source mapping uses range containment against current document-symbol nodes in
  the reference occurrence file.
- Choose the deepest containing symbol by smallest range.
- If no containing symbol is found, use the file node as a fallback source and
  mark the edge `AMBIGUOUS`.
- If the reference points outside the current workspace or to an untracked file,
  skip the canonical edge and record a route diagnostic count. Do not create
  external placeholder nodes in VS-10.

The source spike should also answer whether the pinned analysis API exposes a
stable symbol identity that can be adopted cheaply. If it does, add it to
`properties_json` and raw evidence. Do not rewrite existing node IDs in VS-10
unless the migration is small and fully covered.

## Persistence Flow

Add a new persistence path instead of expanding the existing document-symbol
function into a mixed route.

Recommended high-level flow:

```text
start extraction_run
start rust.document_symbols route status for each file being refreshed
persist document symbols
record document-symbol route observations
complete document-symbol route status
close stale document-symbol nodes and contains edges

start rust.references workspace route status
extract references from current symbols
upsert references edges
insert reference occurrences
insert edge evidence
record reference route observations
complete rust.references route status
close stale reference edges
finish extraction_run complete
```

If any step after the run starts fails:

- mark any in-progress route status as failed with diagnostics;
- finish the extraction run as failed;
- do not stale-close rows for failed routes.

Use one run for the combined workspace refresh so document-symbol and reference
facts share provenance. The route status rows keep freshness separate inside
that run.

## Tests

Add focused tests at each boundary.

Store tests:

- route status start, complete, and fail;
- route observation uniqueness;
- document-symbol stale node closing;
- document-symbol stale `contains` edge closing;
- reference stale edge closing;
- failed route does not close stale rows;
- re-observed stale row is reopened by `upsert_node` or `upsert_edge`.

Rust facade tests:

- reference extraction returns at least one reference from `crates/wip`;
- declaration is not persisted as a reference when excluded or filtered;
- file paths and UTF-16 ranges convert correctly.

Extractor mapping tests:

- maps a reference occurrence to the deepest enclosing symbol;
- falls back to the file node with `AMBIGUOUS` confidence when no enclosing
  symbol exists;
- skips external/untracked references and records diagnostics;
- groups repeated reference locations into one canonical edge with multiple
  evidence rows and `weight` equal to the current run's location count.

Persistence tests:

- writes `references` edge;
- writes `reference` occurrence for the target symbol at the source range;
- writes `textDocument/references` evidence;
- records route observations;
- closes a removed reference edge on a later successful run.

Visualizer backend tests:

- projection can return a `references` edge;
- node details summarize incoming/outgoing `references`;
- edge details return reference evidence.

Smoke tests:

- extend `semantic-graph-smoke-tests` with the workspace references command or
  a direct provider/persister route;
- update README smoke counts if the report output changes.

## Acceptance Criteria

VS-10 is complete when all of the following are true:

- the store has first-class route status and route observation tables;
- document-symbol routes record status and observations;
- successful document-symbol reruns close stale document-symbol-owned nodes and
  `contains` edges;
- failed routes do not close stale rows;
- the Rust facade exposes provider-backed references through the pinned
  in-process `rust-analyzer` crates;
- the workspace references command refreshes symbols and references in one
  user-facing command;
- current reference facts persist as canonical directed `references` edges;
- reference occurrences and edge evidence preserve source proof;
- repeated runs do not duplicate canonical reference edges;
- removing a reference and rerunning the route soft-closes the corresponding
  `references` edge;
- visualizer edge and node details can inspect the new relation without schema
  errors;
- README smoke counts are updated if changed;
- the validation commands pass without warnings.

## Risks And Decisions To Preserve

- Workspace-scoped references are more expensive than file-scoped references,
  but they avoid incorrect freshness semantics for VS-10.
- Current symbol identity is range-sensitive. VS-10 records and tests this
  limitation rather than hiding it.
- External references are skipped in VS-10. Placeholder external nodes need a
  separate identity policy.
- Occurrences and edge evidence remain historical proof. Canonical currentness
  is represented by `nodes.valid_to_run_id`, `edges.valid_to_run_id`, and route
  observations.
- `context = "symbol"` is intentionally conservative. Read/write/type/import
  subtyping should wait until the provider mapping can support it accurately.
