# VS-10: C# Extraction Commands And `csharp-ls-lib`

## Goal

Build a C# extraction path equivalent in shape to the current Rust workflows in
`crates/semantic-graph-extract`, using the `csharp-ls` CLI as the runtime C#
language server and `submodules/csharp-language-server` as the checked-in source
reference for protocol behavior.

The intended user-facing result is a C# command family parallel to:

- `rust-file`
- `rust-file-deleted`
- `rust-document-symbols`
- `rust-crate-document-symbols`
- `rust-workspace-document-symbols`
- `rust-workspace-references`
- `rust-workspace-calls`
- `rust-workspace-all`

The likely implementation shape is a new `crates/csharp-ls-lib` Rust crate that
acts as the typed facade. Unlike `rust-analyzer-lib`, it cannot be a direct Cargo
path dependency on the language engine because `csharp-language-server` is an
F#/.NET LSP server distributed as a .NET tool. Treat the process boundary as the
facade boundary: the Rust crate owns `csharp-ls` launch, JSON-RPC/LSP lifecycle,
request/response typing, and workspace worker reuse.

Install the runtime tool with:

```sh
dotnet tool install --global csharp-ls
csharp-ls --help
```

## Current Evidence

- `crates/rust-analyzer-lib` is the Rust facade over checked-in
  `submodules/rust-analyzer` crates. It exposes workspace loading, source file
  discovery, document symbols, references, outgoing calls, a single analysis
  worker, and a worker pool.
- `crates/semantic-graph-extract/src/main.rs` defines the Rust command surface.
  The default `rust-file` path extracts symbols, references, and calls for one
  file with one worker, then persists file-scoped route freshness and stale
  closing.
- `crates/semantic-graph-extract/src/workspace_all/` persists document symbols
  first, then runs relation routes against a reused worker pool.
- `crates/semantic-graph-extract/src/model/graph_language.rs` and
  `provider_id.rs` already include `GraphLanguage::CSharp` and
  `ProviderId::csharp_language_server`.
- `crates/semantic-graph-extract/src/model/route_name.rs` only has Rust route
  names today.
- `crates/semantic-graph-extract/src/persist/extraction_persister.rs` has
  several Rust assumptions that must be generalized before C# relation routes
  are reliable, especially route names, deleted-file handling, user-facing
  error messages, and `node_id(workspace_id, "rust", ...)` checks.
- `submodules/csharp-language-server/src/CSharpLanguageServer/Handlers/DocumentSymbol.fs`
  returns hierarchical `DocumentSymbol[]` when the client advertises hierarchy
  support. It also emits a synthetic root `SymbolKind.File` node for the
  document.
- `submodules/csharp-language-server/src/CSharpLanguageServer/Handlers/References.fs`
  backs `textDocument/references` with Roslyn
  `SymbolFinder.FindReferencesAsync`.
- `submodules/csharp-language-server/src/CSharpLanguageServer/Handlers/CallHierarchy.fs`
  implements `textDocument/prepareCallHierarchy` and
  `callHierarchy/incomingCalls` through Roslyn `FindCallersAsync`.
  `callHierarchy/outgoingCalls` deliberately returns `None`.
- `submodules/csharp-language-server/src/CSharpLanguageServer/Roslyn/Solution.fs`
  loads `.sln`, `.slnx`, or project files through `MSBuildWorkspace`.
- `submodules/csharp-language-server/tests/CSharpLanguageServer.Tests/Tooling.fs`
  is the best local reference for the LSP client lifecycle: start server,
  send `initialize`, send `initialized`, answer required client callbacks, then
  issue normal LSP requests.

## Non-Goals

- Do not modify `submodules/csharp-language-server` for the first slice.
- Do not require building or linking the submodule for normal extraction. Use
  the installed `csharp-ls` CLI as the runtime process.
- Do not build a bespoke C# semantic analyzer when the LSP can return the fact.
- Do not assume C# outgoing call hierarchy exists. Use incoming call hierarchy
  plus reference-derived candidate targets to compensate for the missing
  `callHierarchy/outgoingCalls` implementation.
- Do not change the durable SQLite schema unless implementation proves a real
  schema gap. The existing store already accepts `csharp` workspace and file
  languages.

## Command Surface

Add these commands to `semantic-graph-extract`:

- `csharp-file [--db <DB>] [--workspace-root <ROOT>] [--solution <SLN_OR_SLNX>] [--symbols|--references|--calls] <FILE>`
- `csharp-file-deleted [--db <DB>] [--workspace-root <ROOT>] <FILE>`
- `csharp-document-symbols --workspace-root <ROOT> [--solution <SLN_OR_SLNX>] --project-path <PROJECT_OR_ROOT> --file <FILE>`
- `csharp-project-document-symbols --workspace-root <ROOT> [--solution <SLN_OR_SLNX>] --project-path <PROJECT>`
- `csharp-workspace-document-symbols --workspace-root <ROOT> [--solution <SLN_OR_SLNX>]`
- `csharp-workspace-references --workspace-root <ROOT> [--solution <SLN_OR_SLNX>]`
- `csharp-workspace-calls --workspace-root <ROOT> [--solution <SLN_OR_SLNX>]`
- `csharp-workspace-all --workspace-root <ROOT> [--solution <SLN_OR_SLNX>]`

Keep `--symbols`, `--references`, and `--calls` mutually exclusive for
`csharp-file`, matching `rust-file`.

For C# calls, use `textDocument/prepareCallHierarchy` plus
`callHierarchy/incomingCalls` for each callable target. Store directed
`caller --calls--> callee` edges exactly like Rust, but record
`lsp_method = "callHierarchy/incomingCalls"` in raw metadata and evidence.

## Facade Crate

Create `crates/csharp-ls-lib` and add it to the workspace.

Public facade responsibilities:

- Locate and launch the installed `csharp-ls` CLI, defaulting to `csharp-ls` on
  `PATH`.
- Provide a narrow override for the binary path for tests and non-global tool
  installs.
- Surface a clear setup error that tells the user to run
  `dotnet tool install --global csharp-ls` and verify with `csharp-ls --help`
  when the binary is missing.
- Initialize the server with C# document-symbol hierarchy support.
- Support optional `--solution` by passing the server's `-s`/`--solution`
  setting or equivalent initialization config.
- Answer required server-to-client JSON-RPC calls. Do not reuse the existing
  extractor `LspStdioClient` as-is, because it ignores inbound server requests
  with IDs. Model the required no-op/config handlers on the submodule test
  client: `workspace/configuration`, `window/workDoneProgress/create`, and
  `client/registerCapability`.
- Expose typed methods:
  - `load_workspace(root, solution_override) -> CSharpWorkspaceModel`
  - `workspace_source_files(model) -> Vec<PathBuf>`
  - `project_source_files(model, project_path) -> Vec<PathBuf>`
  - `document_symbols_for_files(paths) -> Vec<(PathBuf, Vec<DocumentSymbol>)>`
  - `references_for_symbol(target) -> ResolvedReferenceSet`
  - `incoming_calls_for_symbol(target) -> ResolvedIncomingCallSet`
  - `file_semantic_work(work) -> FileSemanticResult`
- Provide `CSharpLsWorker` and `CSharpLsWorkerPool` equivalents to the Rust
  facade from the first implementation. A pool size of one should be the
  correctness baseline, but the public workflow should already queue work across
  long-lived `csharp-ls` worker processes.

Source discovery should mirror `csharp-language-server` workspace loading rules:

1. If `--solution` is supplied, use that `.sln` or `.slnx`.
2. Otherwise discover `.sln`/`.slnx` under the workspace root and prefer the
   one with the most projects, matching the submodule's `selectPreferredSolution`.
3. If no solution is available, discover `.csproj`/`.fsproj`.
4. Collect C# source files from loaded project compile items, excluding build
   output and generated artifacts. A filesystem glob can be a temporary smoke
   fallback, but it should not be the final workspace discovery mechanism.

## C# Configuration

Add a dedicated C# config section to `.refactor-radar/config.toml` instead of
overloading the existing Rust-oriented `[extractor]` worker settings.

Example:

```toml
[csharp]
binary = "csharp-ls"
solution = "SemanticGraph.Visualizer.slnx"
log_level = "warning"
features = []
process_workers = 1
reference_process_workers = 0
call_process_workers = 0
startup_timeout_ms = 120000
request_timeout_ms = 30000
```

Planned fields:

- `binary`: command or absolute path for the language server; defaults to
  `csharp-ls`.
- `solution`: optional `.sln` or `.slnx` path relative to the workspace root or
  config file directory. CLI `--solution` wins over config.
- `log_level`: maps to `csharp-ls --loglevel`; default should be quiet enough
  for extraction runs, probably `warning`.
- `features`: maps to `csharp-ls --features`; keep empty by default and enable
  `metadata-uris` or `razor-support` only when a route needs them.
- `process_workers`: total `csharp-ls` process workers for C# workspace routes.
- `reference_process_workers` and `call_process_workers`: optional split counts
  for relation routes. If both are zero, split `process_workers` using the same
  high-level strategy as Rust route jobs.
- `startup_timeout_ms`: timeout for launching and initializing each worker.
- `request_timeout_ms`: timeout for individual LSP requests.

Resolution precedence:

1. explicit C# CLI flags such as `--solution`, `--csharp-ls`, or worker counts;
2. `[csharp]` config values;
3. conservative defaults.

Do not silently map Rust `analysis_workers` to C# process workers. A
`csharp-ls` process is much heavier than an in-process `rust-analyzer-lib`
analysis worker, so C# needs its own defaults and validation. The shared
`[extractor]` section can still provide language-neutral mode/job defaults only
when the implementation documents that fallback explicitly.

Implementation tasks:

- Add `RawCSharpConfig` and `CSharpConfig` to `semantic-graph-config`.
- Add `Config::csharp()` and tests for defaults, parsing, invalid zero worker
  counts, invalid timeouts, and CLI override behavior.
- Add a C# extractor plan resolver that produces a `ResolvedCSharpExtractorPlan`
  with binary path, solution, feature flags, process worker counts, and
  timeouts.
- Update README config examples after the first working C# command lands.

## Extractor Provider

Add `crates/semantic-graph-extract/src/providers/csharp_ls/`.

The provider should parallel `RustAnalyzerProvider`:

- `CSharpLsProvider::new()`
- `extract_document_symbol_batch`
- `extract_csharp_references`
- `extract_csharp_calls`
- `discover_csharp_project_source_files`
- `discover_csharp_workspace_source_files`
- mapper helpers for already-loaded facade results, so worker and workspace-all
  paths do not re-query document symbols unnecessarily.

Create `CSharpDocumentSymbolMapper`.

Mapper details:

- Set provider to `ProviderId::csharp_language_server()`.
- Set language to `GraphLanguage::CSharp`.
- Reuse the generic LSP range conversion and symbol-key building helpers where
  possible.
- Use C#-appropriate qualified names, preferably dot-separated namespaces and
  containing types.
- Special-case the synthetic `SymbolKind.File` root emitted by
  `csharp-language-server`. The store already creates a file node, so either
  unwrap the root and map its children as top-level file contents, or map it in
  a documented way that avoids duplicate file-like graph structure.
- Preserve raw `DocumentSymbol` JSON and include facade metadata:
  `facade = "csharp-ls-lib"` and `lsp_method = "textDocument/documentSymbol"`.

Reference extraction should:

- Build reference targets from C# document symbols using each symbol's
  `selection_range.start`.
- Query `textDocument/references` through the facade with
  `IncludeDeclaration = false` unless a test proves declarations are needed.
- Reuse the existing symbol-index approach to map occurrence locations to the
  deepest containing source symbol, with file fallback as `AMBIGUOUS`.
- Store route metadata as `csharp.references`.

Call extraction should:

- Select callable document symbols in the same spirit as
  `csharp-language-server`'s `isCallableSymbol`: methods, constructors,
  properties, fields, and events.
- For each callable target, run `prepareCallHierarchy` and then
  `callHierarchy/incomingCalls`.
- Map each incoming call to `caller --calls--> target`.
- Resolve caller and callee to persisted C# symbol keys. Skip external or
  unresolved callers with explicit summary counters, like the Rust call route.
- Store route metadata as `csharp.calls` and raw method
  `callHierarchy/incomingCalls`.

## C# Call-Hierarchy Compensation

`csharp-ls` does not implement `callHierarchy/outgoingCalls`, but this should
not block C# call edges. Treat incoming call hierarchy as the canonical C# call
primitive and reverse it into the same durable `caller --calls--> callee` graph
shape.

Workspace route:

1. Build callable targets from the workspace document-symbol graph.
2. Query `textDocument/prepareCallHierarchy` for each callable target.
3. Query `callHierarchy/incomingCalls` for each prepared item.
4. Convert each incoming result to a directed call edge from `From` to the
   original target item.
5. Map `FromRanges` to call occurrences in the caller file.
6. Skip external or unresolved callers with explicit counters.

File-scoped route:

1. Refresh or load the changed file's document symbols.
2. Build relation context from the workspace symbol graph, matching the Rust
   file route's broader relation context.
3. Run the C# references route first in full `csharp-file` mode.
4. Build a candidate callee set from fresh reference occurrences whose
   occurrence file is the changed file and whose target symbol is callable.
5. Add callable symbols declared in the changed file to the same candidate set.
   This captures callers into the changed file.
6. Query incoming calls for the candidate set.
7. Retain call occurrences where the caller file is the changed file or the
   callee symbol is declared in the changed file.
8. Persist the retained calls under the file-scoped `csharp.calls` route and
   close stale file-scoped call observations for that file.

This compensates for missing outgoing call hierarchy without building a bespoke
semantic analyzer. It costs extra reference work, but it keeps incremental C#
call refresh possible and preserves the same edge direction as Rust.

Acceptance tests for this compensation:

- file A calls a method in file B; running `csharp-file A.cs` refreshes the
  `A.method --calls--> B.method` edge;
- file B's method is called by file A; running `csharp-file B.cs` refreshes the
  same edge through the callee-declared-in-file path;
- a removed callsite in file A is closed as stale by the file-scoped call route;
- unresolved/external incoming callers are counted and skipped, not persisted as
  ambiguous call edges.

Longer term, keep an optional spike to implement real outgoing calls upstream in
`csharp-language-server` using Roslyn semantic model or `IOperation`. That is an
optimization path, not a blocker for this repo's C# call route.

## RPC Contract LSP-Lite

Add a protocol-contract layer that uses LSP-like concepts for RPC/framework
bridges. This should not be a repo-specific extractor and should not be tied to
one serialization system. The implementation shape should be a small generated
or scaffolded LSP-lite provider per supported RPC framework.

Each provider should expose the same contract-level surface:

- contract document symbols: methods, routes, messages, request DTOs, response
  DTOs, and error DTOs;
- contract definitions: where a method/route is declared or dispatched;
- contract references: clients/callers that invoke a method/route;
- contract implementations: server handlers that implement a method/route;
- DTO links: params/request/result/response/error type relationships;
- evidence ranges and raw provider metadata.

The first provider should be JSON-RPC because this repo's bridge is JSON-RPC.
It should extract framework-neutral graph facts such as:

```text
jsonrpc.method:graph.projection
  --handled_by--> rust:function:handle_graph_projection
  --accepts--> rust:struct:GraphProjectionParamsDto
  --returns--> rust:struct:GraphProjectionDto
  --errors_as--> rust:struct:JsonRpcErrorDto
```

When C# client extraction exists, the same contract node should connect to the
client side:

```text
csharp:method:GetProjectionAsync
  --calls_rpc--> jsonrpc.method:graph.projection
```

Planned provider model:

- define a small `ContractProvider` interface in Rust with LSP-inspired methods
  such as `contract_symbols`, `contract_references`, `contract_definitions`,
  `contract_implementations`, and `contract_details`;
- generate or scaffold one provider crate/module per RPC framework so each
  provider handles its own syntax and conventions behind the same interface;
- keep provider output language-neutral enough for the shared SQLite graph:
  `rpc.method`, `rpc.handler`, `rpc.client_call`, `rpc.params_type`,
  `rpc.result_type`, `rpc.error_type`;
- make JSON-RPC the first implementation, then add other RPC/framework
  providers only when there is a concrete project need.

This layer is the cross-language bridge. Rust and C# LSP extraction still own
language symbols, references, and calls; RPC LSP-lite providers connect those
language symbols through first-class protocol contract nodes.

## Single-File Workflow

Implement `csharp-file` after batch document symbols and references work.

Target behavior:

- Default mode extracts document symbols, references, and calls where supported.
- `--symbols` refreshes only file document symbols.
- `--references` refreshes only file-scoped C# references and requires the file
  symbols to already exist in the database.
- `--calls` refreshes only file-scoped C# calls and requires symbols to already
  exist.

Use one `CSharpLsWorker` per command, mirroring `rust-file`.

For file-scoped calls, be conservative:

- Query incoming calls for callable symbols declared in the file.
- To capture outgoing calls from the changed file, use the C# call-hierarchy
  compensation strategy: identify callable workspace targets referenced from
  the file, query incoming calls for those targets, then retain callsites whose
  `FromRanges` are in the changed file.
- Full `csharp-file` should run references before calls so the call route can
  use fresh reference-derived candidate callees.

## Workspace Workflow

Implement `csharp-workspace-all` as the C# equivalent of `rust-workspace-all`:

1. Discover workspace C# source files.
2. Extract and persist document symbols for all files.
3. Extract and persist workspace references.
4. Extract and persist workspace calls through incoming call hierarchy.
5. Close stale route observations for `csharp.document_symbols`,
   `csharp.references`, and `csharp.calls`.

Use `CSharpLsWorkerPool` for this route from the beginning. The default pool can
still contain one process, but `csharp-workspace-all --jobs` and `[csharp]`
worker settings should map to long-lived `csharp-ls` worker processes so the C#
workflow stays structurally close to the fastest Rust implementation.

Keep the default worker count conservative and measure it. Multiple `csharp-ls`
processes may each load their own `MSBuildWorkspace`, so higher worker counts
should be opt-in through CLI/config until smoke data proves a better default.
