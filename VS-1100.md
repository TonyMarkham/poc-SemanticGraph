# VS-1100: Phase 1 Implementation Plan For `semantic-graph-query`

## Purpose

Define the implementation plan for Phase 1 of [VS-100.md](VS-100.md):
creating the durable, transport-neutral read-only query crate for the
SemanticGraph SQLite store.

This plan follows the accepted decisions in [VS-1000.md](VS-1000.md). In
particular:

- `crates/semantic-graph-query` is the durable query boundary.
- The current Blazor/JSON-RPC visualizer is only a local testbed and prior-art
  consumer.
- MCP transport, MCP SDK selection, HTTP behavior, extraction tools, Codex
  skills, custom agents, and installers are not Phase 1 work.
- Existing SemanticGraph database configuration compatibility must be
  preserved; do not rename or migrate `.refactor-radar/config.toml`.

## Goal

Add a new workspace crate:

```text
crates/semantic-graph-query
```

The crate owns SQLite-backed, read-only query behavior and transport-neutral
read models for:

- stats;
- node search;
- node details;
- edge details;
- projection;
- neighbors;
- shortest path;
- file summary;
- route status.

The crate must be usable by the later MCP server and by any optional local
testbed adapter without inheriting visualizer-specific DTO names or JSON-RPC
shape.

## Current Evidence

Existing query prior art lives in:

- `crates/semantic-graph-visualizer-server/src/query/graph_query_service.rs`
- `crates/semantic-graph-visualizer-server/src/query/sqlite_read_pool.rs`
- `crates/semantic-graph-visualizer-server/src/tests/projection.rs`

That code already implements read-only SQLite access for:

- projection;
- node details;
- edge details;
- node search.

The durable schema lives in:

- `crates/semantic-graph-store/migrations/01_create_graph_store.sql`
- `crates/semantic-graph-store/migrations/02_route_freshness.sql`

The important tables for Phase 1 are:

- `workspaces`;
- `extraction_runs`;
- `files`;
- `nodes`;
- `edges`;
- `occurrences`;
- `edge_evidence`;
- `extraction_route_status`;
- `route_observations`.

The existing visualizer query tests seed fixture data through
`semantic-graph-db-manager`, which is the right pattern to reuse for
`semantic-graph-query` fixture tests. Do not make tests depend on hand-written
SQL row sets when existing writer APIs can create realistic graph state.

## Non-Goals

- Do not implement `semantic-graph-mcp-server`.
- Do not choose or add a Rust MCP SDK.
- Do not add HTTP transport.
- Do not add mutating extraction tools.
- Do not generate or install Codex skills, custom agents, or `.codex` config.
- Do not make the visualizer server the public query boundary.
- Do not expose arbitrary SQL, raw file reads, or shell commands.
- Do not change database migrations unless a query cannot be implemented
  correctly without an index. If an index is needed, justify it with the query
  it supports.
- Do not change `.refactor-radar/config.toml` discovery behavior.

## Crate Ownership

`semantic-graph-query` should own:

- public transport-neutral read models;
- read-only SQLite connection setup;
- query parameter validation that is independent of transport;
- server-side limit clamping;
- JSON parsing for graph `properties_json`, `raw_json`, and diagnostics fields;
- typed query errors using `thiserror` and `error-location`;
- fixture-backed tests for every public query method.

`semantic-graph-query` should not own:

- JSON-RPC DTOs;
- MCP tool schemas;
- visualizer DTOs;
- CLI argument parsing;
- database path discovery policy beyond accepting an explicit database path;
- graph mutation or extraction orchestration.

Callers should resolve database paths before constructing the query service.
This keeps Phase 1 compatible with the existing `.refactor-radar/config.toml`
path while avoiding a new config policy in the query crate.

## Workspace Changes

Add the new crate to `Cargo.toml`:

```toml

    ...
    "crates/semantic-graph-query",
    ...
]

[workspace.dependencies]
semantic-graph-query = { path = "crates/semantic-graph-query" }
```

Expected direct dependencies for `semantic-graph-query`:

- `error-location`;
- `serde`;
- `serde_json`;
- `sqlx`;
- `thiserror`;

Expected dev-dependencies:

- `semantic-graph-db-manager`;
- `tokio`.

Avoid a dependency on `semantic-graph-visualizer-server`. If a dependency on
`semantic-graph-store` is useful, keep it one-way from query to store and check
that it does not create a cycle with the current workspace graph.

## Proposed Module Shape

Keep modules small and follow the repository's Rust style: one primary type per
file, explicit `crate::...` imports, no `super` imports, and no glob imports.

Suggested shape:

```text
crates/semantic-graph-query/src/lib.rs
crates/semantic-graph-query/src/error/mod.rs
crates/semantic-graph-query/src/error/query_error.rs
crates/semantic-graph-query/src/error/result.rs
crates/semantic-graph-query/src/service/mod.rs
crates/semantic-graph-query/src/service/graph_query_service.rs
crates/semantic-graph-query/src/sqlite/mod.rs
crates/semantic-graph-query/src/sqlite/read_only_pool.rs
crates/semantic-graph-query/src/sqlite/json_value.rs
crates/semantic-graph-query/src/sqlite/like_pattern.rs
crates/semantic-graph-query/src/model/mod.rs
crates/semantic-graph-query/src/model/*.rs
crates/semantic-graph-query/src/row/mod.rs
crates/semantic-graph-query/src/row/*.rs
```

Rows should stay private implementation details. Public models should be stable
enough for MCP and local adapters to wrap without depending on visualizer naming.

## Public API Shape

Start with a single service constructed from a database path:

```rust
pub struct GraphQueryService {
    database_path: PathBuf,
    max_limit: i64,
}
```

Candidate methods:

```rust
impl GraphQueryService {
    pub fn new(database_path: PathBuf) -> Self;

    pub async fn stats(&self) -> QueryResult<GraphStats>;

    pub async fn search_nodes(
        &self,
        request: NodeSearchRequest,
    ) -> QueryResult<NodeSearchResults>;

    pub async fn node_details(
        &self,
        request: NodeDetailsRequest,
    ) -> QueryResult<NodeDetails>;

    pub async fn edge_details(
        &self,
        request: EdgeDetailsRequest,
    ) -> QueryResult<EdgeDetails>;

    pub async fn projection(
        &self,
        request: ProjectionRequest,
    ) -> QueryResult<GraphProjection>;

    pub async fn neighbors(
        &self,
        request: NeighborsRequest,
    ) -> QueryResult<NodeNeighbors>;

    pub async fn shortest_path(
        &self,
        request: ShortestPathRequest,
    ) -> QueryResult<GraphPath>;

    pub async fn file_summary(
        &self,
        request: FileSummaryRequest,
    ) -> QueryResult<FileSummary>;

    pub async fn route_status(
        &self,
        request: RouteStatusRequest,
    ) -> QueryResult<RouteStatusResults>;
}
```

Use request structs rather than long argument lists where a query has optional
filters or limits. Request structs make later MCP tool mapping direct without
polluting the query crate with MCP-specific schemas.

## Model Guidelines

Public read models should:

- include node ids and edge ids for follow-up queries;
- include occurrence ids and edge evidence ids where available;
- include stale state through `valid_to_run_id` where relevant;
- keep `properties_json`, `raw_json`, and `diagnostics_json` as
  `serde_json::Value` or `Option<Value>`;
- use deterministic ordering for stable tests and agent transcripts;
- avoid visualizer-specific names such as `GraphNodeDto`;
- keep text fields exact in structured fields;
- leave transcript sanitization for Phase 2 MCP text rendering unless a Phase 1
  text summary helper is added.

Recommended core model names:

- `GraphStats`;
- `ExtractionRunSummary`;
- `NodeSearchResult`;
- `NodeSearchResults`;
- `NodeSummary`;
- `NodeDetails`;
- `NodeOccurrence`;
- `NodeRelationSummary`;
- `EdgeSummary`;
- `EdgeEndpoint`;
- `EdgeDetails`;
- `EdgeEvidence`;
- `GraphProjection`;
- `ProjectionMetadata`;
- `NodeNeighbors`;
- `GraphPath`;
- `GraphPathStep`;
- `FileSummary`;
- `RouteStatus`;
- `RouteStatusResults`.

## Query Contracts

### Stats

Return database-wide counts and latest extraction metadata:

- workspace count;
- file count;
- active node count;
- stale node count;
- active edge count;
- stale edge count;
- occurrence count;
- edge evidence count;
- route status count;
- latest extraction runs ordered by `started_at` and id.

This becomes the Phase 2 backing query for `graph_stats`.

### Node Search

Search active nodes where `valid_to_run_id IS NULL` by:

- `nodes.name`;
- `nodes.display_name`;
- `nodes.qualified_name`;
- `files.path`.

Preserve the current visualizer behavior first, including escaped `LIKE`
patterns and deterministic ranking. The schema has `node_search` FTS prior art,
but do not switch search engines in Phase 1 unless the implementation also
tests equivalent behavior and documents the changed ranking.

Return bounded results with node id, kind, label, qualified name, language, file
path, and `valid_to_run_id`.

### Node Details

Return one node by id with:

- core node fields;
- file path;
- container summary;
- `first_seen_run_id`, `last_seen_run_id`, and `valid_to_run_id`;
- parsed `properties_json`;
- active incoming and outgoing relation summaries;
- occurrences with ids, run ids, roles, ranges, file paths, enclosing node id,
  and parsed raw JSON.

The current visualizer query counts only active edges for relation summaries.
Keep that behavior unless a request flag explicitly asks for stale relations.

### Edge Details

Return one edge by id with:

- source and target endpoint summaries;
- relation, context, confidence, confidence score, and weight;
- `first_seen_run_id`, `last_seen_run_id`, and `valid_to_run_id`;
- parsed `properties_json`;
- edge evidence with ids, run ids, provider, LSP method, file path, range, and
  parsed raw JSON.

This should preserve current visualizer evidence behavior while exposing stale
state explicitly.

### Projection

Return a bounded active graph projection:

- selected active symbol nodes;
- related file nodes for selected symbols;
- active edges where both endpoints are selected;
- metadata with database path, requested limit, applied limit, node count, and
  edge count.

The first implementation can preserve the current visualizer selection
algorithm. The important Phase 1 change is ownership: the algorithm lives in
`semantic-graph-query`, and visualizer DTOs adapt to it.

### Neighbors

Return bounded incoming and outgoing active neighbors for a node id.

Each neighbor row should include:

- direction;
- edge summary;
- adjacent node summary;
- relation;
- confidence;
- optional file path;
- stale state for both edge and adjacent node.

Support relation and direction filters if they are simple to express as bound
SQL parameters. Do not add broad graph traversal options here; shortest path is
the separate traversal query.

### Shortest Path

Return a bounded path between two node ids using active edges only.

Implementation guidance:

- validate source id, target id, maximum depth, and maximum visited nodes;
- load bounded adjacency from SQLite with bound parameters;
- run breadth-first search in Rust for the first slice;
- return node and edge summaries in path order;
- return an empty path result when no path is found rather than an error;
- return `NotFound` only when either endpoint node does not exist.

Keep traversal limits small and explicit because this query will later be
agent-facing through MCP.

### File Summary

Return a file-oriented view for one workspace file path:

- workspace id and root URI;
- file row and file node when present;
- active contained symbol summaries;
- active edges touching symbols in that file, bounded by a limit;
- route statuses for file-scoped routes matching that file;
- latest workspace-scoped route statuses for the same workspace.

Accept file path as a database `files.path` value, not an arbitrary filesystem
read path. This query must not read source files from disk.

### Route Status

Return route freshness rows filtered by:

- workspace id or root URI where provided;
- route name where provided;
- scope where provided;
- scope key where provided;
- file path where provided.

Include:

- route;
- scope;
- scope key;
- file path when available;
- provider and provider version;
- content hash;
- last started run id;
- last complete run id;
- last status;
- parsed diagnostics JSON;
- updated time.

Use deterministic ordering by workspace, route, scope, scope key, provider, and
id.

## Limits And Validation

Add server-side maximums in the query crate even though MCP is later work:

- default limit for list-like queries;
- maximum limit for node search;
- maximum limit for projection;
- maximum limit for neighbors;
- maximum traversal depth and visited-node count for shortest path;
- maximum number of route status rows.

Validation belongs in `semantic-graph-query` when the rule is transport-neutral:

- blank node id is invalid;
- blank edge id is invalid;
- blank search query is invalid;
- limit must be positive and no larger than the crate maximum;
- shortest path endpoints must be non-blank;
- file summary path must be non-blank and treated as a database path string,
  not a filesystem path to read.

Transport-specific validation and error code mapping remain outside the query
crate.

## Error Handling

Follow the repository's typed error style:

- use `thiserror`;
- use `error-location`;
- do not add `anyhow`;
- expose `QueryError` and `QueryResult<T>`;
- provide constructors such as `database`, `json`, `invalid_params`, and
  `not_found` with `#[track_caller]`.

The later MCP server can map these errors to MCP or JSON-RPC error responses.

## Visualizer Compatibility Work

After `semantic-graph-query` has fixture-tested methods, update
`semantic-graph-visualizer-server` to consume it for its existing RPC methods:

- `graph.projection`;
- `graph.node_details`;
- `graph.edge_details`;
- `graph.search_nodes`.

Keep visualizer DTOs inside `semantic-graph-visualizer-server`. Add small
adapter conversions from query models to visualizer DTOs if needed. Do not move
visualizer JSON-RPC names or DTO names into `semantic-graph-query`.

When this step is complete, the visualizer server should no longer own the
shared query implementation. It may keep RPC parameter parsing, RPC error
mapping, server config, and UI-testbed DTOs.

## Test Plan

Add fixture-backed tests in `crates/semantic-graph-query`.

Reuse the current visualizer fixture pattern:

- create a temporary SQLite database;
- start `semantic-graph-db-manager::WriteManager`;
- run migrations;
- seed workspaces, files, nodes, edges, occurrences, evidence, extraction runs,
  route statuses, and route observations through writer APIs;
- shut down the writer;
- query through `GraphQueryService`.

Minimum query tests:

- `stats` returns active and stale counts plus latest run metadata.
- `search_nodes` finds by name, qualified name, display name, and file path.
- `search_nodes` escapes `%`, `_`, and `\`.
- `node_details` returns metadata, active relation summaries, occurrences, and
  stale state.
- `edge_details` returns endpoints, confidence, properties, evidence, and stale
  state.
- `projection` includes selected symbols, related file nodes, and active edges.
- `neighbors` returns bounded incoming and outgoing active neighbors.
- `neighbors` respects direction and relation filters if implemented.
- `shortest_path` returns a path for connected active nodes.
- `shortest_path` returns an empty result for disconnected active nodes.
- `shortest_path` rejects blank ids and excessive limits.
- `file_summary` returns the file row, file node, contained symbols, touching
  edges, and route freshness.
- `route_status` returns file-scoped and workspace-scoped route rows with parsed
  diagnostics.
- stale nodes and edges are either excluded from active queries or surfaced with
  `valid_to_run_id` where the query contract says details can return stale
  entities by exact id.

Visualizer compatibility tests:

- existing `semantic-graph-visualizer-server` projection tests continue to pass;
- existing RPC validation tests continue to map invalid params and not-found
  query errors correctly.

## Implementation Sequence

1. Add the `semantic-graph-query` crate skeleton and workspace entries.
2. Add `QueryError`, `QueryResult`, read-only SQLite pool setup, JSON parsing,
   and LIKE escaping helpers.
3. Move or reimplement projection, node details, edge details, and node search
   query logic from visualizer prior art into the new crate with neutral model
   names.
4. Add the shared fixture seed module in query tests and port the existing
   visualizer query assertions to the new crate.
5. Implement `stats`.
6. Implement `neighbors`.
7. Implement `shortest_path`.
8. Implement `file_summary`.
9. Implement `route_status`.
10. Update the visualizer server to depend on `semantic-graph-query` and adapt
    query models to its existing DTOs.
11. Remove duplicated query ownership from the visualizer server.
12. Run validation and clean up any warnings before presenting the phase as
    complete.

Keep each patch narrow enough that failures identify one query surface at a
time.

- [ ] Workspace wiring is complete: `crates/semantic-graph-query` exists,
  `Cargo.toml` lists it as a workspace member, and
  `[workspace.dependencies]` exposes `semantic-graph-query`.
- [ ] Public API is complete: `semantic-graph-query` exports a read-only
  `GraphQueryService`, typed request models, typed response models,
  `QueryError`, and `QueryResult`.
- [ ] Query coverage is complete: `GraphQueryService` implements stats, node
  search, node details, edge details, projection, neighbors, shortest path,
  file summary, and route status.
- [ ] Transport neutrality is preserved: `semantic-graph-query` does not export or
  depend on MCP tool schemas, JSON-RPC DTOs, visualizer DTOs, CLI argument
  types, Axum types, or installer/Codex asset types.
- [ ] Read-only behavior is enforced: the query service opens SQLite through
  read-only connection options and contains no graph mutation, extraction,

- [ ] Active graph semantics are tested: active list/traversal queries filter on

  `valid_to_run_id` when an exact id resolves to stale graph state.

  fixture-backed tests for every public query method listed in this plan.
- [ ] Visualizer compatibility is preserved: `semantic-graph-visualizer-server`

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| Query models accidentally inherit visualizer DTO shape. | Name public models neutrally and keep visualizer adapters in the visualizer crate. |
| Shortest path becomes expensive on large graphs. | Enforce max depth and max visited nodes before traversal, and test limit behavior. |
| File summary is mistaken for a filesystem read. | Treat the input as a `files.path` database value only and never read source files. |
| Route freshness semantics drift from extraction behavior. | Seed route status through `semantic-graph-db-manager` APIs in tests. |
| Config compatibility is disturbed. | Keep database path resolution in callers and do not edit `.refactor-radar/config.toml` behavior. |
| Visualizer compatibility masks duplicate query ownership. | Remove or privatize visualizer query SQL after adapting it to `semantic-graph-query`. |

## Deferred Decisions

- MCP SDK choice remains Phase 2 work.
- MCP resources and tool schemas remain Phase 2 work.
- HTTP transport remains later work and must follow the VS-100 loopback and API
  key requirements if added.
- Mutating extraction MCP tools remain Phase 4 work and must stay explicitly
  gated.
- Codex skill, custom-agent, and installer paths remain Phase 3 and later work
  governed by VS-1000.
