# VS-2000: Full Text Extraction Indexing Plan

## Purpose

Define the implementation plan for adding full text search extraction to the
semantic database through the existing `crates/semantic-graph-extract` binary.

This supersedes the narrower idea of only activating the existing `node_search`
FTS table. The new direction is a repository-wide file-content extraction
route:

```sh
semantic-graph-extract fts
```

The command scans the workspace, indexes text from every eligible file, and
skips only files or directories excluded by `.refactor-radar/config.toml` or
by explicit command flags.

## Goal

Add a maintained full text index for source and project files:

- add an `[fts]` section to `semantic-graph-config`;
- support `[fts].ignore-directories`;
- support `[fts].ignore-files`;
- add `semantic-graph-extract fts`;
- support `--no-rust`, `--no-csharp`, and `--no-submodules`;
- persist file-content FTS data in the existing SQLite semantic database;
- track FTS extraction runs and stale indexed documents;
- build a case-insensitive trigram substring candidate index for later
  query work;
- store original indexed text so later query work can verify case-sensitive,
  literal, and regex matches without reading arbitrary files;
- keep full text indexing separate from semantic node and edge extraction;
- leave MCP, query-service, and visualizer integration for a later plan.

## Research Basis

The extraction index should be designed around developer file search semantics,
not natural-language search semantics:

- JetBrains Find in Files exposes separate whole-word, match-case, regex,
  scope, exclusion, and file-mask controls.
- ripgrep separates ignore-case, smart-case, fixed-string, regex, glob, and
  ignore-file behavior.
- SQLite FTS5 is case-independent by default and its trigram tokenizer supports
  general substring matching.
- SQLite FTS5 trigram `case_sensitive = 0` gives the broad ignore-case
  candidate behavior needed for default Find-in-Files style search.
- SQLite FTS5 trigram `case_sensitive = 1` enforces case in the index, but then
  the index can optimize `GLOB` only, not `LIKE`; this is too narrow for the
  single primary extraction index.
- Therefore the extract-side index should store original content and build a
  case-insensitive trigram candidate index. Later query work can enforce
  case-sensitive, literal, and regex semantics by verifying candidates against
  stored original content.
- SQLite FTS5 trigram queries need at least one three-character non-wildcard
  sequence to use the index. One- and two-character literal queries require a
  later exact-scan or specialized fallback in the read path.
- Porter stemming is English-language oriented and should not be used for code
  search, where punctuation, casing, and exact identifiers matter.

References:

- <https://www.sqlite.org/fts5.html#the_trigram_tokenizer>
- <https://www.jetbrains.com/help/idea/finding-and-replacing-text-in-project.html>
- <https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md>

## Non-Goals

- Do not replace Rust or C# language-server-backed semantic extraction.
- Do not index file contents into canonical `nodes` or `edges`.
- Do not treat FTS matches as semantic references, calls, definitions, or
  evidence.
- Do not expose arbitrary SQL.
- Do not add a filesystem watcher.
- Do not require Graphify or another external search engine.
- Do not add app-owned JavaScript to the visualizer.
- Do not add or update MCP tools.
- Do not add `GraphQueryService::search_text`.
- Do not update the visualizer server or Blazor client.
- Do not make submodule exclusion the default unless the user passes
  `--no-submodules` or adds exclusions to config.
- Do not index binary files as text. Binary or non-decodable files should be
  skipped with diagnostics rather than failing the whole extraction.

## User Contract

### Config

Add this section to `.refactor-radar/config.toml`:

```toml
[fts]
ignore-directories = []
ignore-files = []
```

Rules:

- `ignore-directories` excludes matching directories and their descendants.
- `ignore-files` excludes matching file paths.
- Entries are evaluated against normalized workspace-relative paths.
- Path matching must be deterministic across platforms: normalize `\` to `/`
  and reject absolute paths or `..` escapes in config.
- Missing `[fts]` means both arrays default to empty.

The default generated config template should include an `[fts]` section so the
feature is visible, even if both arrays are empty initially.

### CLI

Add a new command:

```sh
semantic-graph-extract fts
```

Supported options:

```sh
semantic-graph-extract fts --no-rust
semantic-graph-extract fts --no-csharp
semantic-graph-extract fts --no-submodules
```

The command should also preserve the existing extractor conventions:

- global `--config` continues to select a config file;
- command-level `--db` may be supported for consistency with existing extract
  commands;
- database resolution should use the same `resolve_cli_database_path` behavior
  as other extractor commands.

`semantic-graph-extract fts` scans from the current workspace root. If an
explicit workspace-root option is added later, it must follow the existing
`--workspace-root` convention used by Rust extraction commands.

### Exclusion Flags

`--no-rust` excludes:

```text
*.rs
```

`--no-csharp` excludes:

```text
*.cs
```

`--no-submodules` excludes every file under every Git submodule directory.
Implement this without requiring network access:

- read submodule paths from `.gitmodules` under the workspace root;
- when a submodule itself has `.gitmodules`, read it recursively and exclude
  nested submodule paths too;
- normalize every submodule path relative to the scan root;
- skip each submodule subtree during discovery;
- do not treat an arbitrary nested `.git` directory as a submodule unless it is
  also listed by `.gitmodules`.

Config exclusions and CLI exclusions are additive. A file is indexed only if it
survives all configured and command-line exclusions.

## Tokenization And Index Semantics

The primary file-content index should prepare for developer Find-in-Files
behavior, not natural-language document search.

Use a SQLite FTS5 trigram index as the required first-class content index:

```sql
tokenize = 'trigram case_sensitive 0'
```

This is the default candidate source that later query/MCP work should use, but
building the read path is outside this plan.

Rules:

- the primary trigram index is case-insensitive;
- normal literal search is substring-oriented, so punctuation-heavy code such
  as `foo::bar`, `get_user(`, `path/to/file`, `Some<T>`, and `=>` can later be
  matched;
- original content must be stored so later case-sensitive, literal, and regex
  query implementations can verify trigram candidates exactly;
- token or identifier search may improve ranking, but must not be the only
  source of truth for later Find-in-Files matches.

Add a secondary term index only as a ranking and convenience surface. It should
index generated terms such as:

- normalized path segments;
- filenames, extensions, and stems;
- whole identifiers;
- camelCase, PascalCase, snake_case, kebab-case, dotted, and namespace
  segments;
- language labels.

Do not use Porter stemming for code. Source text search should not make
`runner`, `running`, and `run` equivalent unless a later natural-language docs
search feature explicitly asks for that behavior.

## Storage Design

Add a new migration:

```text
crates/semantic-graph-store/migrations/03_fts_documents.sql
```

The migration should add canonical FTS document metadata and a content FTS5
table.

Recommended canonical table:

```sql
CREATE TABLE fts_documents (
  id INTEGER PRIMARY KEY,
  workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
  file_id INTEGER NOT NULL REFERENCES files(id),
  language TEXT NOT NULL CHECK (language IN ('rust', 'csharp', 'markdown', 'other')),
  content_hash TEXT NOT NULL,
  byte_len INTEGER NOT NULL,
  indexed_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  first_seen_run_id INTEGER REFERENCES extraction_runs(id),
  last_seen_run_id INTEGER REFERENCES extraction_runs(id),
  valid_to_run_id INTEGER REFERENCES extraction_runs(id),
  properties_json TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(properties_json)),
  UNIQUE (workspace_id, file_id)
);
```

Required primary FTS table:

```sql
CREATE VIRTUAL TABLE fts_document_trigram_ci USING fts5(
  document_id UNINDEXED,
  file_id UNINDEXED,
  path,
  language,
  content,
  tokenize = 'trigram case_sensitive 0'
);
```

The first implementation should let this FTS table store original content so
later case-sensitive verification, literal verification, regex verification,
and snippets do not require arbitrary filesystem reads from read-only query
surfaces.

Optional ranking-helper FTS table:

```sql
CREATE VIRTUAL TABLE fts_document_terms USING fts5(
  document_id UNINDEXED,
  file_id UNINDEXED,
  path,
  language,
  terms,
  tokenize = "unicode61 remove_diacritics 0 tokenchars '_$#@'"
);
```

`fts_document_terms.terms` should be generated by the extractor from path and
identifier-like text. It should help rank and filter; it should not decide
whether a literal Find-in-Files query matches.

Recommended indexes:

```sql
CREATE INDEX idx_fts_documents_workspace_active
  ON fts_documents(workspace_id, valid_to_run_id);

CREATE INDEX idx_fts_documents_file
  ON fts_documents(file_id);
```

Design rules:

- `files` remains the canonical file identity table.
- `fts_documents` tracks active/stale indexed documents.
- FTS virtual tables are derived index data and can be rebuilt from current file
  contents by rerunning `semantic-graph-extract fts`.
- `fts_document_trigram_ci` stores original indexed content in SQLite for the
  first implementation. This is expected and required for later read-only
  search verification.
- Stale FTS documents should be clearly marked so later query work can exclude
  them.

## Write Path

Add DB-manager APIs rather than writing SQL directly from the extractor:

```rust
upsert_fts_document(...)
close_stale_fts_documents_for_workspace(...)
```

`upsert_fts_document` should:

- upsert the row in `files` or require the caller to upsert the file first;
- upsert the row in `fts_documents`;
- clear `valid_to_run_id` when a previously stale document is observed again;
- replace the matching `fts_document_trigram_ci` row;
- replace the matching `fts_document_terms` row if the ranking-helper table is
  implemented in the same phase;
- skip replacing content when the `content_hash` is unchanged, where practical.

`close_stale_fts_documents_for_workspace` should:

- mark active `fts_documents` stale when their `last_seen_run_id` is older than
  the current successful FTS run for the workspace;
- delete matching rows from `fts_document_trigram_ci`;
- delete matching rows from `fts_document_terms` if present;
- run only after a successful FTS scan.

Physically delete stale FTS rows because the content is derived and can be
large. Keep stale state in `fts_documents`.

## Extraction Design

Add an FTS extraction module under `crates/semantic-graph-extract`, for example:

```text
crates/semantic-graph-extract/src/fts/
```

Suggested module responsibilities:

- `fts_config` or use the typed config crate directly;
- `fts_exclusion_set` for config and CLI exclusion matching;
- `fts_file_discovery` for deterministic workspace walking;
- `fts_file_classifier` for language and binary/text decisions;
- `fts_term_builder` for generated path and identifier ranking terms;
- `fts_extraction_runner` for scanning and persistence orchestration;
- `fts_extraction_summary` for command output.

Discovery rules:

- walk the workspace deterministically, sorted by normalized relative path;
- skip directories and files from `[fts]`;
- apply `--no-rust`, `--no-csharp`, and `--no-submodules`;
- include Rust and C# files by default;
- include Markdown and other UTF-8 text files by default;
- skip binary, oversized, unreadable, or non-UTF-8 files with diagnostics.

Language classification:

- `*.rs` -> `rust`;
- `*.cs` -> `csharp`;
- Markdown extensions -> `markdown`;
- everything else that is text -> `other`.

Use SHA-256 content hashes, matching the repository's existing hashing style.

## Route And Run Tracking

Add a route name for FTS extraction:

```text
fts.full_text
```

Provider:

```text
semantic-graph-extract
```

Run behavior:

- create or reuse a mixed workspace rooted at the scan root;
- start an `extraction_runs` row for provider `semantic-graph-extract`;
- start a workspace-scoped route status for `fts.full_text`;
- persist every indexed file through the DB-manager FTS APIs;
- complete the route only after the full scan and persistence pass succeed;
- close stale FTS documents only after route completion;
- mark the run failed if discovery or persistence fails before completion.

The existing `route_observations` table currently restricts `entity_kind` to
`node` and `edge`. Do not force FTS files into fake nodes or edges. Use
`fts_documents.last_seen_run_id` for stale closure unless the route observation
schema is intentionally generalized in the same migration.

## Later Query Integration

Query and MCP integration are intentionally out of scope for this plan.

A later plan should add a read-only `GraphQueryService::search_text` surface and
MCP tool. That later work should use `fts_document_trigram_ci` as the primary
candidate source, verify case-sensitive/literal/regex matches against stored
original content, and use `fts_document_terms` only for ranking or explicit
term search modes.

## Acceptance Tests

Add or update tests proving:

- `[fts]` config parses with `ignore-directories` and `ignore-files`;
- missing `[fts]` defaults to empty exclusions;
- invalid FTS config paths are rejected;
- `semantic-graph-extract fts` parses with the requested flags;
- FTS discovery indexes Rust, C#, Markdown, and other text files by default;
- `--no-rust` excludes `*.rs`;
- `--no-csharp` excludes `*.cs`;
- `--no-submodules` excludes files under submodule roots;
- config directory exclusions skip full subtrees;
- config file exclusions skip matching files;
- binary or non-UTF-8 files are skipped with diagnostics;
- FTS extraction creates `files`, `fts_documents`, and
  `fts_document_trigram_ci` rows;
- if the ranking-helper table is implemented, FTS extraction also creates
  `fts_document_terms` rows;
- the trigram table is configured as case-insensitive;
- stored original content preserves casing for later exact verification;
- direct SQL smoke checks can find candidate rows for punctuation-heavy strings
  such as `foo::bar`, `get_user(`, and `path/to/file`;
- extraction docs or tests record that one- and two-character literal queries
  need later read-path fallback because trigram MATCH cannot candidate them by
  itself;
- rerunning FTS with unchanged content is idempotent;
- removing a file or adding a new exclusion marks its FTS document stale after
  a successful run;
- stale FTS documents are closed without deleting canonical stale state.
